# Резервная копия и восстановление контейнерной установки

Для полного восстановления нужны три части одной установки:

1. Дамп PostgreSQL, снятый от owner-роли, которая видит данные всех организаций.
2. Файловое состояние sync: том `/var/lib/remo` при стандартной конфигурации.
3. Секреты установки, включая прежний `REMO_KEK` и его идентификатор.

Команда `remo backup` создаёт и проверяет **дамп базы**, а не полный архив установки.
Снимок файлов и защищённая копия секретов выполняются дополнительно. Дамп не содержит
паролей ролей PostgreSQL и KEK. Потеря KEK лишит доступа к зашифрованным настройкам и TOTP.
При `REMO_FILES_DRIVER=s3` вместо дискового каталога нужен согласованный снимок бакета;
копирование локального тома не заменяет его.

## Снять согласованную копию

Включите окно обслуживания и остановите всех писателей этой установки: web, sync и
внешние фоновые задания. PostgreSQL оставьте работающим. Используйте compose-файл,
env-файл, имя проекта и образ текущего релиза этой установки. Не подставляйте dev/test URL.
Для исполнения примеров определите функцию, заменив все значения в угловых скобках:

```sh
export REMO_RELEASE='<полный commit текущего релиза>'
export REMO_PRODUCTION_ENV='/srv/<instance>/shared/production.env'
compose() {
  docker compose -p '<имя compose-проекта>' \
    --env-file "$REMO_PRODUCTION_ENV" \
    -f '/srv/<instance>/releases/<commit>/deploy/compose.production.yml' "$@"
}
```

Если identity установки задаёт `REMO_WEB_ALIAS` вне env-файла, экспортируйте и это значение
из её `shared/instance.env`, не исполняя файл как shell-код. Перед любыми операциями
проверьте `compose ps`: это должны быть контейнеры выбранной установки.

1. Задайте `umask 077`, создайте новый каталог резервной копии с правами `700` и перейдите в него.
2. Выполните `compose stop web sync` и остановите дополнительные задания-писатели.
3. Выполните `compose run --rm -T --no-deps db-tools pg_dump -Fc > database.dump`.
4. Проверьте дамп:

   ```sh
   compose run --rm -T --no-deps db-tools pg_restore --file=/dev/null < database.dump
   ```

5. Снимите файловое состояние в том же окне обслуживания:

   ```sh
   compose run --rm -T --no-deps --user 0 \
     -v /absolute/path/to/backup:/backup --entrypoint tar sync \
     -czf /backup/state.tgz -C /var/lib/remo .
   ```

   Этот вызов использует подключение тома sync из compose. Если файлы вынесены через
   `REMO_FILES_DIR` в другой mount, сохраните и его. Отдельно сохраните внешние anchors,
   если конфигурация помещает их вне тома.

6. Сохраните env/секреты с правами `600`, отдельно от публичных файлов и Git. При хранении
   за пределами защищённой машины зашифруйте весь комплект. Не публикуйте вывод env.
7. Запишите версию приложения, commit/image digest, версию схемы и SHA-256 архивов.
8. Запустите sync и web, проверьте health. Храните копию вне исходного VPS.

## Восстановить в отдельную установку

Сначала используйте новую БД и новый том; рабочую установку не перезаписывайте. Загрузите
образы того же релиза. Создайте owner и `remo_app` в новом кластере, задайте новые адреса
подключения в env, сохранив исходный KEK. Проверьте, что все URL указывают на новую БД.
Owner нужен для миграций, runtime использует `remo_app` без superuser/BYPASSRLS.

1. Пока sync/web остановлены, создайте роль приложения штатным инструментом:

   ```sh
   compose run --rm -T --no-deps sync node /app/scripts/db-rls-setup.mjs
   ```

2. В пустую БД восстановите дамп от owner-роли. Требуйте остановки при ошибке:

   ```sh
   compose run --rm -T --no-deps db-tools \
     sh -c 'exec pg_restore --exit-on-error --dbname="$PGDATABASE"' < database.dump
   ```

3. Распакуйте состояние в **новый** том sync, сохранив владельцев и права:

   ```sh
   compose run --rm -T --no-deps --user 0 \
     -v /absolute/path/to/backup:/backup:ro --entrypoint tar sync \
     -xzf /backup/state.tgz -C /var/lib/remo
   ```

4. Проверьте схему, роль приложения и RLS штатными инструментами релиза:

   ```sh
   compose run --rm -T --no-deps sync node release-db.mjs
   compose run --rm -T --no-deps sync node /app/scripts/rls-inventory.mjs --check
   compose run --rm -T --no-deps sync node /app/scripts/db-rls-enable.mjs --check
   ```

5. Запустите sync/web и проверьте health, портал, вход существующего пользователя,
   комнату и WebSocket. Откройте существующее изображение и сравните его хеш с исходным.
   Проверьте чтение ранее зашифрованной настройки без обращения к платному провайдеру,
   затем создайте и сохраните новый объект.

Проверка структуры `pg_restore --file=/dev/null` ещё не доказывает восстановление.
Периодически выполняйте полный цикл на изолированных данных: сравнение содержимого таблиц,
файлов, проверка RLS, вход и работа браузера после запуска. Только после такой проверки
принимайте решение о переключении трафика. Проверка миграции репозитория не выполняет
переключение production и не меняет его данные.
