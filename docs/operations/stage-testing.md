## Два уровня входа

1. Откройте приложение. Сначала браузер попросит **пароль стенда**. Это защита nginx,
   а не форма входа в Ремуку. Данные находятся в локальном приватном файле
   `.config/remo/stage-access.env.local`: `STAGE_HTTP_USER` и `STAGE_HTTP_PASSWORD`.
   Для документации и Mailpit браузер может попросить ту же пару ещё раз.
2. В приложении нажмите **«Войти»** и используйте один из аккаунтов ниже. Пароль аккаунта
   берите из `STAGE_EU_SEED_PASSWORD` для ЕС или `STAGE_RU_SEED_PASSWORD` для РФ в том же
   файле. Это другой пароль, не пароль nginx. После сброса стенда эти значения сохраняются.

Файл имеет права 600, исключён из Git и Docker. Не прикладывайте его к отчёту и не
вставляйте пароли в URL, скриншоты, задачи или таблицу приёмки.

### Если пароль стенда спрашивают снова и снова

1. **Проверьте тип хэша.** Edge работает на Alpine, где системный `crypt()` не умеет
   bcrypt: строка `$2y$` в `stage.htpasswd` означает, что nginx ответит `401` на любой
   пароль, и браузер будет спрашивать бесконечно.

   ```sh
   docker exec stage-nginx sh -c 'cut -d: -f2 /etc/nginx/stage.htpasswd | cut -c1-6'
   ```

   Должно быть `$apr1$`. Пересоздайте файл с `-m` (apr1):

   ```sh
   sudo htpasswd -m -c /srv/stage-nginx/stage.htpasswd tester1
   sudo htpasswd -m /srv/stage-nginx/stage.htpasswd tester2
   ```

   `-c` перезаписывает файл, поэтому остальные строки добавьте заново. Контейнер
   перезапускать не нужно — файл смонтирован и читается на каждый запрос.
2. **Проверьте пару без браузера.**

   ```sh
   curl -s -o /dev/null -w '%{http_code}\n' -u 'tester1:ПАРОЛЬ' https://app.stage.remuka.ru/api/config
   ```

   `200` — пара верна, дело в браузере; `401` — неверны имя, пароль или хэш.
3. **Разные хосты — разные пары в кэше.** `app.stage.*`, `docs.stage.*`, `mail.stage.*` и
   апекс `stage.*` спрашивают отдельно: браузер кэширует данные по хосту и realm. Это
   ожидаемо, а не «слетающий» пароль.
4. **Если просит только при работе в комнате**, дело в WebSocket: `/sync/` стоит за basic
   auth, и браузер должен передать туда сохранённые данные. Проверьте Chrome, Firefox и
   Safari; если какой-то не передаёт — поставьте `auth_basic off` для `location /sync/`
   (сокет всё равно требует сессию), это разрешено §4.1 `spec/stage.md`.

## Что уже проверено

- HTTPS всех восьми адресов, 401 без пароля, исключения для health и платёжных вебхуков.
- Баннер stage, `noindex`, вход тестовым владельцем, запись и повторная загрузка комнаты,
  WebSocket, портал и Mailpit в Chromium.
- Схема 39, RLS на 49 таблицах, роль `remo_app` без superuser и BYPASSRLS.
- По пять тестовых аккаунтов и шесть комнат в каждой зоне; повторный seed не создаёт дубли.
- Сброс обеих баз с восстановлением тестовых данных, очисткой Mailpit и повторной проверкой RLS.
- Тестовые письма с префиксом `[Stage]` в Mailpit; отдельные ежедневные бэкапы stage,
  хранение три дня. Существующее резервное копирование production не отключалось.

Это проверка готовности инфраструктуры, а не заполненный продуктовый чек-лист.
Firefox, Safari, телефон, внешний почтовый провайдер и платёжные провайдеры требуют
отдельной приёмки.

## Как проходить чек-лист

Основной документ — [spec/ui-acceptance.md](../../spec/ui-acceptance.md). Порядок работы:

1. Откройте `/api/health` приложения и запишите в отчёт `version`, `schema`, `commit`,
   зону, дату и браузер. Должны быть `stage: true` и схема 39.
2. Создайте по одной строке результата на **сценарий и зону**: например, `S-20 / ru`
   и `S-20 / eu`. Для сценария, предназначенного только одной зоне, вторую не добавляйте.
3. Сначала пройдите сайт, вход и документы (S-01–S-16), затем холст и совместную работу
   (S-20–S-37), экспорт, справку и настройки. Первую комнату проверяйте новым аккаунтом.
4. Письма подтверждения, приглашения и сброса пароля открывайте в Mailpit нужной зоны.
   Проверка перехода по ссылке возможна уже сейчас; доставку в Gmail/Яндекс, спам и DKIM
   отмечайте отдельно как непроверенные без внешнего драйвера.
5. Для S-90–S-97 войдите оператором и настройте TOTP в своём приложении-аутентификаторе.
   У ЕС и РФ разные операторы и секреты. Сохраните recovery-коды приватно. После reset
   **и после повторного seed** TOTP и recovery-коды нужно настроить заново: seed намеренно
   возвращает оператора в начальное состояние без второго фактора.
6. Интеграционные сценарии проходите после настройки из таблицы ниже. Удаление аккаунтов
   и необратимые действия оставьте на конец; используйте отдельные тестовые аккаунты.
7. Для каждого результата выберите статус из ТЗ: **Готово**, **Частично**, **Не работает**,
   **Не реализовано**, **Не проверено**. Запишите ожидаемое, фактическое и доказательство.
   Если не настроена интеграция, укажите эту причину вместо вывода о дефекте продукта.
8. Для дефекта сохраните шаги и скриншот/видео без ключей, паролей и recovery-кодов.
   После исправления повторите сценарий на новой версии.

Экспорт на stage всегда имеет знак «Stage/Стенд», в том числе на Pro. Он отличается от
тарифного знака Free; при S-51 проверяйте их отдельно. Документы пока допускаются как
черновики: это настройка стенда, а не признак юридической готовности production.

в странице виджета, а разрешённый origin — в CSP приложения. Для iframe поддержка
настраивается на собственном хосте; защита `/app` операторов Chatwoot сохраняется.
Исключения доступа для поддержки не переносятся на `/api` приложения stage.

Не используйте реальные деньги, production-ключи ИИ или почтовые адреса клиентов.
Проверка отказа live-платежей остаётся отдельным пунктом ТЗ; сейчас live-подключений нет.

## Поддержка: Chatwoot на стенде

На стенде поднят Chatwoot CE отдельным compose-проектом `stage-chatwoot` в `/srv/stage-chatwoot`: rails, sidekiq, отдельные PostgreSQL и Redis, своя сеть. Контейнер приложения виден только в сети `edge`, к backend-сети Ремуки он не подключён. Ограничения памяти рассчитаны на 4 ГБ стенда: rails 1.2 ГБ, sidekiq 700 МБ, PostgreSQL 384 МБ, Redis 192 МБ.

| Что | Адрес |
|---|---|
| Чат и виджет | `https://support.stage.remuka.ru/` |
| Вход операторов | `https://support.stage.remuka.ru/app` (сначала пароль стенда, потом учётная запись Chatwoot) |
| Страница виджета | `https://support.stage.remuka.ru/widget.html` |
| Администратор | `support@stage.remuka.ru`, пароль — `ADMIN_PASSWORD` в `/srv/stage-chatwoot/secrets.env` (mode 600, только через `sudo`) |

**Что уже настроено:** аккаунт `Remuka`, канал Website «Помощь в приложении», **Identity Validation включена** (`hmac_mandatory`), pre-chat выключен, сайт канала — `https://app.stage.remuka.ru`. Токены лежат в `/srv/stage-chatwoot/tokens.env`: website token ушёл в страницу виджета, HMAC — в `REMO_SUPPORT_HMAC_SECRET` приложения.

**Как это связано:** Caddy стенда ведёт `support.stage.remuka.ru` в stage-ingress; там `support.conf` отдаёт два статических файла и проксирует остальное в `stage-chatwoot:3000`. Basic auth снят только на хосте поддержки: iframe не может унаследовать пароль стенда, а переписка привязана к подписанной личности. `/app` операторов остаётся за паролем стенда.

**CSP приложения.** Контейнер web отдаёт политику без `frame-src`, поэтому в vhost `app.stage.remuka.ru` (`/srv/stage-nginx/conf.d/stage.conf`) стоит `proxy_hide_header Content-Security-Policy` и своя политика с `frame-src https://support.stage.remuka.ru`. Это правка стенда, не прода: на боевых установках вариант с `frame-src` рендерится при выкладке (`deploy/config.sh`, `render_support_headers`).

**Как проверить обращение:**

1. Войдите владельцем (`owner@stage.remuka.ru`) → «Помощь» в меню аккаунта.
2. Панель должна открыть чат, а в Chatwoot появиться разговор с именем, почтой и тарифом. Названий и содержимого комнат там быть не должно.
3. Ответьте из `https://support.stage.remuka.ru/app` — ответ появляется в панели и приходит письмом.
4. Выйдите из аккаунта приложения при открытой панели: виджет должен сбросить сессию (`reset`), следующий вход — новый разговор.
5. Проверьте, что страницу нельзя встроить с чужого origin: `curl -I https://support.stage.remuka.ru/widget.html` отдаёт `frame-ancestors https://app.stage.remuka.ru`, а без `/app` пароля операторская часть отвечает `401`.

**Повторная установка:** `deploy/stage/chatwoot.compose.yml`, `chatwoot.env.example`, `chatwoot-init.rb` и `nginx-support.conf` лежат в репозитории. Секреты создаются на месте (`SECRET_KEY_BASE`, пароль базы, `ADMIN_PASSWORD`), в git не попадают. Порядок: `up -d postgres redis` → `rails db:chatwoot_prepare` → `chatwoot-init.rb` → `up -d rails sidekiq` → отрендерить страницу виджета с website token → включить `REMO_SUPPORT_*` в `production.env` → перезапустить sync.

**Ограничения стенда:** письма Chatwoot уходят через Postbox **без** белого списка приложения — тестировщикам не стоит вводить чужие адреса. Ресурсы рассчитаны на несколько одновременных разговоров, не на нагрузку. Сброс `stage:reset` базу Chatwoot не трогает: переписка стенда переживает сброс приложения.

## Почта: как проверить до прода

Стенд работает через настоящий SMTP (Postbox), но с белым списком получателей: `REMO_MAIL_ALLOW_RECIPIENTS`. Всё, что не перечислено, получает `status = 'suppressed'`, ссылка вычищается. Поэтому «письма не приходят» почти всегда означает «адрес не в списке», а не сломанную почту.

Второй, полностью безопасный режим — Mailpit (`REMO_SMTP_URL=smtp://mail:1025`): письма никуда не уходят, их видно на `https://mail.stage.remuka.ru`. Он годится для шаблонов, ссылок и токенов, но не для проверки доставки.

**Что проверяется в любом режиме** (шаблоны и ссылки):

1. Поток целиком: регистрация → подтверждение адреса, сброс пароля, приглашение, TOTP-письма, `payment_succeeded`.
2. Ссылка в письме ведёт на `https://app.stage.remuka.ru/...`, а не на прод — откройте её и пройдите до конца.
3. Тема на стенде начинается с `[Stage]` / `[Стенд]`; в письме нет чужих доменов и старых адресов.
4. Адресат, тема, текст RU и EN — переключите язык аккаунта и повторите.
5. Токен одноразовый: второе открытие ссылки отклоняется.

Проверить один шаблон без прохождения формы:

```sh
/srv/stage-ru/remo cli mail-test --to owner@stage.remuka.ru
/srv/stage-ru/remo cli mail-test --to owner@stage.remuka.ru --lang ru
```

Без `--lang` пробник пишет по-английски — это свойство инструмента, а не установки. Реальные письма берут язык получателя. Адрес поддержки в подписи письма берётся из зоны установки (`support@remuka.ru` для РФ), а не из языка письма.

**Что Mailpit не доказывает:** доставку, DKIM/SPF, спам. Если нужен реальный ящик, временно переключите **только stage** на Postbox с белым списком:

```sh
# shared/production.env стенда
REMO_MAIL_DRIVER=smtp
REMO_MAIL_FROM=Ремука <no-reply@remuka.ru>
REMO_SMTP_URL=smtp://<id ключа>:<секрет>@postbox.cloud.yandex.net:587
REMO_MAIL_ALLOW_RECIPIENTS=you@example.com,@example.com
```

Перезапустите sync и проверьте:

```sh
/srv/stage-ru/remo cli mail-test --to you@example.com
```

Письмо на адрес **вне** списка не уйдёт: строка получит `mail_outbox.status = 'suppressed'` с причиной, ссылка будет вычищена. Это защита стенда, а не сбой. В настоящем ящике смотрите: папка «Спам», `Show original` → `SPF: PASS`, `DKIM: PASS`, `DMARC: PASS`, совпадение `From` и домена, рабочую ссылку. После проверки верните `REMO_SMTP_URL=smtp://mail:1025`.

Очередь и ошибки:

```sh
/srv/stage-ru/remo cli mail-dead            # мёртвые письма и код причины
/srv/stage-ru/remo cli mail-dead --retry <id>
```

`dead` означает, что провайдер отказал или ссылка истекла; ссылка у такого письма уже вычищена, поэтому чаще правильный путь — попросить человека запросить письмо заново, а не «оживлять» секрет.

**Перед продом** минимум: `mail:test` на самом проде после выкладки, одно реальное письмо на свой ящик, `mail-dead` пуст, а `REMO_MAIL_BATCH` не больше лимита провайдера.

## Почта: какой env менять

Конфигурация стендов хранится в `/srv/stage-eu/shared/production.env` и
`/srv/stage-ru/shared/production.env`, а не в `/srv/remo/shared/production.env`.
Название файла не определяет тип установки — его задают каталог, база и `REMO_STAGE=1`.
`shared/stage.env` существующие скрипты не читают.

Для текущих проверок ничего менять не нужно: `REMO_MAIL_DRIVER=smtp` и
`REMO_SMTP_URL=smtp://mail:1025` уже направляют письма в Mailpit.

Если нужна внешняя доставка на RU, после подтверждения домена у провайдера замените
настройки **только stage-ru**, например:

```ini
REMO_MAIL_DRIVER=smtp
REMO_MAIL_FROM=Ремука <no-reply@remuka.ru>
REMO_SMTP_URL=smtp://USER:URL_ENCODED_PASSWORD@smtp.example.ru:587
REMO_MAIL_ALLOW_RECIPIENTS=tester@example.com
```

Это пример, не рабочие credentials. Нужны полный hostname, логин, URL-кодированный пароль
и порт: `587` с STARTTLS или `465` с `smtps://`. Одного `smtp://` недостаточно.
В ЕС используйте своего отправителя и свой почтовый сервис. При внешней доставке письма
не будут появляться в Mailpit; получателей вне allow-list сервис подавляет.

После изменения env перезапустите только выбранный стенд:

```sh
ssh deploy@185.171.83.153 '/srv/stage-ru/tools restart'
ssh deploy@185.171.83.153 '/srv/stage-ru/tools mail:test --to tester@example.com'
```

## Сброс, состояние и следующие релизы

Сброс удаляет **все** тестовые аккаунты, комнаты и TOTP выбранного стенда, очищает его
Mailpit и возвращает начальные тестовые данные. Сначала сохраняется бэкап. Другая зона и production
не затрагиваются. Операторская обёртка использует штатные `stage:reset` и `stage:seed`
от owner-роли, затем восстанавливает гранты, применяет и проверяет RLS, и лишь после
этого открывает web. Работающий сервис всегда использует `remo_app`.

```sh
# Выберите одну команду. Перед сбросом сохраните нужные результаты приёмки.
ssh deploy@87.106.94.6 '/srv/stage-eu/tools stage:reset --yes'
ssh deploy@185.171.83.153 '/srv/stage-ru/tools stage:reset --yes'

# Статус: root задаётся явно, чтобы не открыть /srv/remo по умолчанию.
ssh deploy@87.106.94.6 'REMO_ROOT=/srv/stage-eu /srv/stage-eu/remo status'
ssh deploy@185.171.83.153 'REMO_ROOT=/srv/stage-ru /srv/stage-ru/remo status'
```

После reset заново войдите в приложение и настройте TOTP при необходимости.
Новые интеграции и настройки в БД тоже исчезнут; env и пароль nginx сохранятся.

Следующие релизы запускаются из локального репозитория, после коммита изменений:

```sh
REMO_DEPLOY_ENV_FILE=.config/remo/stage-eu.env.local bash deploy/release.sh
REMO_DEPLOY_ENV_FILE=.config/remo/stage-ru.env.local bash deploy/release.sh
```

Каждая команда обновляет только одну зону. Production-профили `com.env.local`,
`ru.env.local` и запуск без выбора stage-профиля для этого не подходят.

## Особенности текущей установки

В отличие от исходного примера `stage.md`, здесь по одному стенду на каждом из двух
существующих VPS. TLS обслуживает действующий Caddy; отдельный nginx за ним проверяет
пароль и не публикует портов. На первом VPS продолжают работать другие проекты.

В серверных nginx-конфигурациях редиректы выполняются после basic auth, HTML помечен
`noindex`, а Docker-алиасы разрешаются повторно, чтобы смена IP контейнера при обновлении
не оставляла старый upstream. Файлы: `/srv/stage-nginx/conf.d/stage.conf` и
`/srv/stage-nginx/compose.json` на каждом сервере.

Для таймеров `remo-backup@stage-eu` / `remo-backup@stage-ru` установлен drop-in с явным
`REMO_ROOT`. Без него текущий контроллер по умолчанию выбирает `/srv/remo`.

При запуске обнаружен дефект упаковки: сервер импортировал `scripts/billing-prices.mjs`,
но runtime-образ не содержал эту папку. Исправление в `deploy/Dockerfile` сохраняет
относительное расположение `apps/sync` и `scripts`; копия diff и исходного Dockerfile
сохранена в `shared/` каждого stage. Во время подготовки эта правка уже вошла в локальный коммит
`498871bd5f058d62f78b7338b2640ab51e6a22f4`. На stage код приложения соответствует
указанному в начале коммиту; упаковка содержит эту правку. Дополнительно нормализованы
права статических файлов для nginx: распаковка с umask 077 не должна приводить к 403
для значков, скриптов темы и шаблонов. Эта строка Dockerfile и операционная инструкция
пока не закоммичены; сохраните их перед следующим запуском release.sh.
