# Жёсткая приёмка «характера»: экран = макет

Статус: принято 24.11.2026 (запрос владельца). Применяется ко всем заданиям T1–T27 и ко всем
следующим, у которых есть артборд. Задание на инструмент — T28.

## 0. Почему

Скриншоты владельца 24.11 показывают, что принятые задания разошлись с макетами:

**Вход (`App-Auth`, T15)**
| Макет | Продукт |
| --- | --- |
| Отдельный экран-карточка «С возвращением» | Модальное окно поверх пустой главной «Войдите, чтобы увидеть комнаты» на сером фоне |
| Один заголовок; ниже «Нет аккаунта? Своя комната — за минуту» | Два заголовка подряд («Вход» и логотип «Ремука») + вкладки «Войти / Создать аккаунт» |
| «Забыли?» — в строке подписи «Пароль» | «Забыли пароль?» — отдельной ссылкой под полем |
| Одна кнопка «Войти» во всю ширину | «Отмена» + «Войти», крестик в синей рамке фокуса |

**Рейка инструментов (`App-ToolsBars`, T8)**
| Макет | Продукт |
| --- | --- |
| Панель с радиусом 16, отступ 8, кнопки 44 × 44 с радиусом 10 | Панель-«таблетка» (полное скругление) |
| Выбранный инструмент — жёлтый квадрат 10 px радиуса с чернильной рамкой | Выбранный — жёлтый круг |
| Отменить / повторить — в той же панели, под чертой | Отдельная вторая «таблетка» |

Обе разницы не ловятся текущими проверками: эталоны (`spec/baselines`) сравнивают продукт с
продуктом же, а не с макетом. Отчёты принимались по чек-листу без снимков «рядом».

## 1. Правило приёмки

**Задание с артбордом принимается только при сравнении «макет | продукт» рядом для каждого
состояния артборда, в обеих темах и на двух ширинах.** Без этих снимков задание возвращается
без рассмотрения.

## 2. Что сравниваем и с какой точностью

| Слой | Допуск | Класс расхождения |
| --- | --- | --- |
| **Структура**: какие элементы есть, их порядок, вложенность, модальный это экран или страница | ноль | A |
| **Тексты**: заголовки, подписи, кнопки, ошибки (голос ADR-265) | дословно | A |
| **Цвета**: только токены; цвета бренда (коралл, жёлтый, фиолетовый, люди) | точное совпадение токена | A |
| **Контраст, фокус, роли ARIA** | `e2e:a11y` чистый | A |
| **Форма**: радиусы, толщина рамок, жёсткие тени, форма выбранного | точное значение | B |
| **Размеры и отступы** | ± 2 px | B |
| **Шрифт**: кегль, начертание, межбуквенный | точное | B |
| **Движение**: что анимируется, длительность, «Спокойные анимации» | как в прототипе | B |
| **Мелочи**: субпиксели, сглаживание, перенос строк при другой ширине | — | C |

**Решение:** любое **A** — задание возвращается. **B** — не больше 3 на экран, каждое
оформлено как дефект с датой исправления; больше 3 — возврат. **C** — список в отчёт.

Отклоняться от макета разработчик **может только с решением владельца**, записанным в ADR (как
ADR-274 про перенос WIP). «Так проще в коде» — не основание.

## 3. Как проходит приёмка

1. **Эталоны макета** уже лежат в `docs/design/reference/<артборд>/<состояние>-<ширина>.png`
   (300 снимков, 1440 и 390 px; тёмная тема — артборды `App-Dark-*`). Генерируются офлайн
   из исходников `pnpm mockups:shots`; список у каждого задания — в его разделе «Эталоны PNG».
2. **Фикстуры макета.** Для каждого артборда — сценарий в `e2e/fixtures/mockup/` с теми же
   данными, что в макете (организация «Ромашка», комната «Ретро · спринт 14», люди Аня, Илья,
   Миша, тексты стикеров), чтобы снимки были сопоставимы.
3. **Снимки продукта.** `pnpm accept:shots <артборд>` проходит фикстуру, снимает те же
   состояния и собирает страницу «макет | продукт | разница» (`accept-report/index.html`) с
   процентом отличающихся пикселей по зонам. Процент — подсказка, не решение.
4. **Протокол.** Разработчик заполняет таблицу §4 по каждому состоянию и прикладывает отчёт.
5. **Ревью.** Claude проверяет отчёт, сам снимает 2–3 состояния на стенде и классифицирует
   расхождения A/B/C. Итог — «принято» или «возврат» со списком.
6. **Подпись владельца** на итоговой странице сравнения.

## 4. Форма протокола (на каждое состояние)

| Артборд · состояние | Тема · ширина | Структура | Тексты | Цвета | Форма | Размеры | A | B | C | Снимок |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| App-Auth · вход | светлая · 1440 | ✗ модалка вместо экрана | ✗ «Вход» | ✓ | ✗ | — | 3 | 1 | 0 | ссылка |

## 5. Что уже известно сейчас

Расхождения §0 — дефекты класса A в принятых T15 и T8. Они возвращаются в работу задачей T28
(шаг «пересдача»), вместе с полным проходом по всем экранам волн 0–8 по этому протоколу.
