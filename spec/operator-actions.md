# Операторская консоль: действия, защита возврата, QR

ADR-262. Статус: 2026-11-23. Продолжает `spec/operator.md` (ADR-259, этапы 3–4) и
`spec/totp.md` (ADR-260, этап 4). Снимает ограничения, записанные в `guide/operator/`.

## 0. Что сейчас и что меняется

| Ограничение (из `guide/operator/`) | Причина | Что делаем |
| --- | --- | --- |
| Повтор `billing:refund` после успешного возврата вернёт деньги ещё раз в пределах остатка | ключ идемпотентности `operator-refund:<payment>:<refunded>:<amount>` меняется, как только первый возврат записан | §1: возврат требует подтвердить ожидаемый остаток; в консоли — ключ на форму |
| Нет QR при подключении TOTP, только ключ и `otpauth`-ссылка | `spec/totp.md` §8 не доделан | §2 |
| Консоль только читает; деньги и меры — через CLI | этап 3 `spec/operator.md` не начат | §3–§4: действия в Клиентах, разделы Деньги и Жалобы |
| Команды CLI не требуют второго фактора | CLI защищён только SSH | §5: CLI спрашивает код оператора, от имени которого действует |
| Нет писем о TOTP, очистки вызовов | `spec/totp.md` этап 4 не сделан | §6 |
| «—» вместо нуля, «сервер» в журнале | так и задумано | **не меняем**: «нет данных» ≠ «ноль», действие системы ≠ действие человека |

Что уже правильно и сохраняется:
- `PostgresStore.recordRefund` блокирует платёж (`for update`) и считает остаток по возвратам
  `pending` и `succeeded`. Два возврата сверх суммы платежа невозможны.
- Технический повтор (обрыв связи после ответа провайдера) безопасен: тот же ключ уходит
  провайдеру и упирается в `unique` на `refunds.idempotency_key`.
- `operator:grant/revoke` и `mfa:reset` остаются **только в CLI** (ADR-259, ADR-260): кто
  управляет операторами и вторым фактором — решается с доступом к серверу.

## 1. Защита возврата от повторного запуска человеком

Опасный случай: оператор не увидел вывода (закрылся терминал, пропала сеть), запускает
команду снова, а первый возврат уже прошёл. Остаток уменьшился, ключ новый, провайдер
возвращает деньги второй раз.

### 1.1 CLI

- Новый обязательный параметр `--expect-refunded <minor-units>`: сколько, по мнению оператора,
  уже возвращено по платежу. `customer:show` и карточка в консоли показывают это число рядом с
  платежом («возвращено: 0 ₽» → `--expect-refunded 0`).
- Проверка — внутри той же транзакции, что блокирует платёж: если фактическая сумма возвратов
  `pending + succeeded` не равна ожидаемой — отказ без обращения к провайдеру:
  `[billing:refund] pay_… : already refunded 1 990 ₽, expected 0 ₽; check customer:show before repeating`.
  Код выхода — 3 (отличается от ошибки провайдера — 1), чтобы скрипты могли различить.
- Порядок: сверка остатка → запрос к провайдеру → запись. Сверку нужно повторить в
  транзакции записи (`recordRefund`), потому что между сверкой и записью возможен второй
  оператор. Расхождение на шаге записи после успешного ответа провайдера — **не** отказ:
  возврат уже произошёл, его записываем, а в вывод и журнал — предупреждение
  `refund.concurrent` с обоими операторами.
- Ключ идемпотентности в CLI: `operator-refund:<payment>:<expect-refunded>:<amount>`. При
  совпадении ожидания с фактом он равен нынешнему, поведение технического повтора не меняется.
- `--expect-refunded` без значения или с нечислом — ошибка разбора аргументов. Переходного
  режима «без параметра» нет: команда используется вручную, ломать нечего.

### 1.2 Консоль

- Форма возврата при открытии получает `requestId` (UUID) и текущее «возвращено» с сервера.
  Ключ: `operator-refund:<payment>:console:<requestId>`. Двойной клик, повтор после таймаута,
  обновление страницы с повторной отправкой — один возврат.
- Сервер сверяет «возвращено» из формы с фактом так же, как CLI (§1.1). Расхождение → `409
  REFUND_STATE_CHANGED`, форма показывает новое значение и просит подтвердить заново.

### 1.3 Отметка оплаты, кредит, тариф

- `billing:mark-paid` уже идемпотентна (на оплаченном счёте ничего не меняет) — без изменений.
- `billing:credit` и `billing:grant` в консоли — тот же `requestId` в ключе; в CLI — новый
  необязательный `--request-id`, без него поведение прежнее (повтор кредита добавит второй
  кредит — это видно в карточке и записано в руководстве).

## 2. QR при подключении TOTP

- Клиент рисует QR из `otpauth://` (`spec/totp.md` §4 шаг 2) рядом с ключом. Ключ остаётся —
  это текстовая альтернатива QR для доступности и для ручного ввода.
- Генерация на клиенте, SVG, без сети и без CDN; CSP не меняется. Библиотека — небольшая, без
  зависимостей, лицензия MIT/ISC (например, `qrcode-generator`), проходит `pnpm audit:prod` и
  проверку лицензий. Если подходящей нет — собственная реализация не делается, остаётся ключ.
- `otpauth://` и секрет не уходят в логи, метрики и ошибки клиента; QR не кэшируется
  (`Cache-Control: no-store` на ответе с секретом уже должен быть — проверить).
- Сканируется Яндекс Ключом, Google Authenticator, 1Password, Bitwarden; issuer
  «Ремука (РФ)» / «Remuka (EU)» отображается.

## 3. Действия в консоли

### 3.1 Общие правила для каждого изменяющего маршрута

1. Роль оператора проверяется так же, как для чтения: не оператор — `404`.
2. `assertOperatorStepUp` — код не старше 15 минут (`spec/totp.md` §6); иначе `403
   MFA_REQUIRED`, консоль показывает окно кода и повторяет действие после ввода.
3. Тело запроса: параметры действия, `reason` (обязательна, от 10 символов), `requestId`
   (UUID из формы). Повтор с тем же `requestId` возвращает результат первого вызова.
4. **Одна реализация на CLI и консоль.** Маршрут вызывает ту же функцию, что и команда
   (`apps/sync/operator-billing.mjs`, `operator-abuse.mjs` и т.д.); различается только вход и
   вывод. Копия логики в маршруте — дефект ревью.
5. В аудит пишется `channel: "console"` или `"cli"`; журнал консоли показывает канал.
6. Перед отправкой — окно подтверждения с последствиями человеческим языком: «Вернуть 1 990 ₽
   организации «Ромашка». Подписка Pro закончится сейчас. Клиенту уйдёт письмо». Кнопка
   активна после ввода причины.
7. Ответ сервера — итог действия; консоль обновляет карточку, а не рисует оптимистично.

### 3.2 Маршруты

Снаружи — `/api/operator/...`, в сервисе — `/operator/...`.

| Маршрут | Команда-образец | Что делает |
| --- | --- | --- |
| `POST /operator/payments/<id>/refund` `{amount?, expectRefunded, reason, requestId}` | `billing:refund` | §1.2 |
| `POST /operator/invoices/<id>/mark-paid` `{reason, requestId}` | `billing:mark-paid` | ручная оплата по счёту |
| `POST /operator/orgs/<id>/credit` `{amount, currency, reason, requestId}` | `billing:credit` | кредит на услуги |
| `POST /operator/orgs/<id>/grant` `{plan, until, reason, requestId}` | `billing:grant` | выдать или продлить тариф |
| `POST /operator/measures` `{kind, target, reason, requestId}` | `abuse:link-disable`, `abuse:board-hide`, `abuse:org-suspend` | мера по жалобе; `target` — ссылка на комнату или id организации |
| `POST /operator/measures/<id>/revert` `{reason, requestId}` | `abuse:revert` | снять меру |

Маршрутов для `operator:*`, `mfa:reset`, `account:delete --now` в консоли **нет**.

### 3.3 Таблица идемпотентности

Новая таблица `operator_requests (request_id uuid primary key, operator_id, route, result jsonb,
created_at)`; хранение 30 дней (чистится вместе с прочими сроками, `spec/account-deletion.md`
§8). Повтор `requestId` от другого оператора или на другой маршрут — `409`. Ссылка на
пользователя — через `operator_id`; добавить в карту ссылок удаления аккаунта
(`account-deletion.mjs`) как `delete` после срока хранения или анонимизацию — как у
`operator_actions`.

## 4. Разделы консоли

### 4.1 Клиенты (действия)

В карточке организации — кнопки действий §3.2, у каждого платежа — «возвращено» и кнопка
«Вернуть». Действие, недоступное по состоянию (платёж не оплачен, всё возвращено), — кнопка
неактивна с подсказкой, а не ошибка после отправки.

### 4.2 Деньги

| Вкладка | Содержимое | Действия |
| --- | --- | --- |
| Подключения | провайдер, режим (test/live), статус, дата последнего события; **без секретов** | только чтение; создание и смена ключей — CLI `billing:providers` |
| Мёртвые события | вебхуки, которые не удалось обработать: провайдер, тип, ошибка, попытки | только чтение в этом ТЗ; повтор — если в CLI уже есть команда, через неё же (§3.1 п. 4), если нет — отдельной задачей |
| Возвраты | последние возвраты: кто, когда, сумма, статус у провайдера, канал | ссылка на карточку |
| Кредиты и ручные оплаты | последние записи с автором и причиной | ссылка на карточку |

### 4.3 Жалобы

- Список открытых мер (`abuse:list --open`): вид, цель, автор, причина, дата.
- «Новая мера»: вставить ссылку на комнату или найти организацию → выбрать вид → причина.
- «Снять меру» у каждой открытой.
- Письма администраторам — те же, что у CLI (`operator_action`), с адресом обжалования зоны.

## 5. Второй фактор в CLI

Сейчас CLI-команды с деньгами и мерами требуют `--as <оператор>`, но не проверяют, что это он:
под одним пользователем сервера могут работать несколько человек.

- `billing:refund`, `billing:credit`, `billing:grant`, `billing:mark-paid`, `abuse:*` (кроме
  `abuse:list`) требуют, чтобы у оператора `--as` был подтверждённый TOTP, и спрашивают код:
  интерактивно при TTY, иначе из `--code`. Проверка — `matchTotp` с защитой от повтора шага,
  как при входе; резервный код тоже принимается и расходуется.
- Неверный код — отказ без действия; 5 неверных подряд — блок команд от этого оператора на 15
  минут. Попытки лежат в `mfa_cli_attempts` (схема 39), поэтому блок переживает перезапуск
  команды, а верный код удаляет строки оператора.
- Аудит пишет `mfa: "totp"` или `"recovery"`.
- `operator:grant/revoke`, `mfa:reset` — без кода: ими восстанавливают доступ, когда второго
  фактора нет. Их защищает доступ к серверу.
- Переменная `REMO_OPERATOR_CLI_MFA=0` отключает проверку **только при `REMO_STAGE=1`**
  (`spec/stage.md` §5) — для скриптов стенда.

## 9. Приёмка

Проходится на стенде (`spec/stage.md`); сценарии S-91, S-95, S-96, S-97 из
`spec/ui-acceptance.md` должны стать «Готово».

- [ ] `billing:refund … --expect-refunded 0` после успешного возврата того же платежа —
      отказ с кодом 3, провайдер не вызывался (журнал провайдера в тестовом кабинете).
- [ ] Два терминала одновременно возвращают один платёж — сумма возвратов не больше платежа;
      при гонке после ответа провайдера — запись `refund.concurrent`.
- [ ] Двойной клик «Вернуть» в консоли и обновление страницы с повторной отправкой — один
      возврат; `operator_requests` содержит одну строку.
- [ ] Возврат из консоли через 20 минут после ввода кода — окно кода; после ввода —
      выполняется; в журнале `channel: console`, `mfa: totp`.
- [ ] Команды §5 без кода или с неверным — отказ; резервный код срабатывает один раз.
- [ ] QR сканируется Яндекс Ключом и Google Authenticator; ключ рядом; в логах сервиса и
      консоли браузера нет `otpauth://`.
- [ ] Меры: создать по ссылке, снять; письма администраторам с адресом обжалования зоны.
- [ ] Маршрутов `operator:*`, `mfa:reset` в консоли нет (404 на любой придуманный путь).
- [ ] Логика каждого действия вызывается из одной функции для CLI и консоли (ревью + тест на
      одинаковые записи аудита).
- [ ] Письма TOTP приходят на RU и EN; неподтверждённые записи старше суток удаляются.
