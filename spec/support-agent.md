## 1. Цель, объём и приоритет требований

Пользователь получает короткую проверяемую помощь по своей версии Ремуки и может перейти
к человеку в том же разговоре. Команда видит, решена ли проблема и доволен ли клиент
поддержкой в целом, независимо от участия AI. Отдельно через браузер настраивается агент
и контролируются расходы по провайдерам и моделям за выбранный период.

Это внешний `remo-support-agent`, отдельный репозиторий и релиз. В ядре остаётся только
существующая опциональная интеграция поддержки; Chatwoot хранит переписку. Реализация
экспортов знаний принадлежит сборщику документации в этом репозитории. Новая схема сервиса
независима от схемы продукта: это ТЗ не требует следующей версии схемы Remuka.

Требования этого документа заменяют §4, §6 и агентские части §7–§9 `support.md`.
§2 исходного ТЗ сохраняет контракт идентификации и агрегированного контекста. При конфликте
по агенту действует этот документ; старые ADR не редактируются.

**В MVP входят:** RU/EN, Agent Bot для Website inbox, передача человеку, поиск в знаниях,
оценка решения проблемы, импорт CSAT, панели качества/расходов/знаний/настроек, управляемые подключения
провайдеров, версии промптов, бюджеты, аудит, метрики, бэкап и повторяемое развёртывание.
Email-канал подключается отдельно в Chatwoot; пригодность оценок и интерактивных сообщений
для него должна пройти отдельную приёмку. Его работа не подразумевается успехом Website.

**За рамками MVP:** изменения комнат, платежей и прав, произвольный браузинг, shell/SQL
инструменты, автоматическое обучение на переписке, голос, несколько сотрудничающих агентов,
собственная система тикетов, сравнение сотрудников по индивидуальному рейтингу.

«Без необходимости» в запросе трактуется как **без правки исходников, входа по SSH,
пересборки и перезапуска для обычной смены промпта, модели, подключения или лимита**.
Добавление нового протокола провайдера и изменение неизменяемых правил требуют релиза.

## 2. Роли и границы доступа

| Роль | Разрешено |
|---|---|
| Пользователь поддержки | Свой разговор, оценка решения своей проблемы и удовлетворённости поддержкой через Chatwoot |
| Оператор | Просмотр качества и решений, переход в разрешённые ему разговоры Chatwoot, проверка черновиков, пауза автоответов |
| Аналитик | Агрегаты качества/расходов и обезличенный CSV; без промптов, секретов, текста переписки и индивидуальных ссылок на обращения |
| Администратор поддержки | Права оператора, подключения и секреты, промпты, тарифы, публикация/откат, бюджеты, возобновление автоответов |
| Сервис агента | Только разрешённые account/inbox Chatwoot, утверждённые знания, агрегированный контекст Remuka |

Роли действуют в одной установке `(zone, environment, chatwoot_account)`; роль администратора
поддержки не даёт доступа к комнатам или администраторам другой установки. Оператор видит
метаданные только разрешённых inbox; сам текст открывается в Chatwoot с его проверкой прав.
Глобальные бюджеты, модельные настройки и расходы видны администратору и аналитику;
оператору — состояние доступности агента и причины передачи, без глобальных финансовых сумм.

Операторская панель использует **OIDC Authorization Code + PKCE**, серверную сессию
`httpOnly`, `Secure`, защиту CSRF и серверное соответствие групп ролям. MFA задаётся на IdP
и обязательно для администраторов. Проверять issuer, audience, подпись, state, nonce и срок;
короткоживущие коды не журналировать. Локальная открытая регистрация отсутствует.
Назначение ролей в IdP доверено его администратору; соответствие групп задаётся при установке
и не редактируется обычным промптом. Контакт Chatwoot и его email не являются операторской
учётной записью. Чужие cookie Chatwoot не разбираются, пользовательские API-токены не
вставляются в браузер панели. Наличие IdP пока не подтверждено: его подключение — явная
инфраструктурная задача перед вводом панели, а не уже работающая возможность.

## 3. Архитектура и источники истины

```text
Widget → Chatwoot → подписанный webhook → intake → PostgreSQL queue → worker
                                                         │             │
OIDC → /agent/ → configuration / dashboards                │             ├─ knowledge tools
                                                         │             ├─ read-only context
Сборка guide/help → manifest → index revision               │             └─ provider adapter
                                                                       │
Chatwoot ← delivery/reconciliation ← outbox ← проверка ответа / handoff ──┘
                                           │
                            decision events + feedback + usage ledger
                                           │
                           dashboard projections / metrics export
```

Один Docker image сервиса, роли процессов `api` и `worker`; отдельный статический frontend.
Node.js поддерживаемой LTS-ветки, TypeScript, PostgreSQL с pgvector; версии фиксируются
в lockfile и image digest. PostgreSQL даёт задания, блокировки, outbox, FTS и векторный
индекс; новый Redis, отдельная векторная СУБД и agent framework не обязательны.
Возможен общий кластер PostgreSQL с инфраструктурой VPS, но нужны отдельная БД, роли
мигратора и runtime, лимиты соединений, бэкапы и отсутствие доступа к таблицам продукта
и Chatwoot. Наличие pgvector на конкретном VPS проверяется до установки, не предполагается.

| Данные | Источник истины |
|---|---|
| Сообщения, состояние разговора, итоговый CSAT | Chatwoot |
| Подтверждение решения проблемы, запрос оценки, связь повторных обращений | БД сервиса; контакт и разговор подтверждаются данными Chatwoot |
| Промпт, подключения, тарифы, лимиты | Неизменяемые опубликованные ревизии БД агента |
| Знания | Утверждённый артефакт сборки и manifest; индекс воспроизводим |
| Попытки вызовов и стоимость | Usage ledger агента |
| Дашборды и внешний metrics sink | Восстанавливаемые проекции событий; не альтернативный журнал |

## 4. Мультиязычные материалы и совместимость

**KB-01.** Не поддерживать разные руководства вручную. Сборщик создаёт из `guide/`:

| Путь относительно `/guide/` | Содержимое |
|---|---|
| `llms.ru.txt`, `llms.en.txt` | Индекс соответствующего языка |
| `llms-full.ru.txt`, `llms-full.en.txt` | Полные страницы соответствующего языка |
| `llms.txt` | Существующий индекс с сохранением текущих разделов/ссылок и добавлением ссылок на языковые выгрузки |
| `llms-full.txt` | Совместимый английский экспорт; байтово равен `llms-full.en.txt` одной сборки |

Старые адреса не исчезают и не переключаются на русский по заголовку запроса. У каждого
языка стабильный адрес, ETag/content hash и явный `Content-Type` с UTF-8. Генератор и CI
проверяют наличие обеих локалей и актуальность переводов. Изменение публичной выгрузки
сопровождается RU/EN обновлением страницы портала о материалах для AI.

**KB-02.** Сборка выпускает `support-knowledge.manifest.json` и архив с разрешёнными
Markdown-файлами guide/help. Manifest: `format_version`, `build_id`, `product_release`,
`product_commit`, `docs_commit`, `schema_version`, `built_at`, локали, список документов.
У документа: стабильный `doc_id` для обеих локалей, `locale`, `title`, `audience`,
`source_type`, ссылка на страницу и заголовок, относительный путь, SHA-256 и статус перевода.
`manifest_id` — хеш канонического manifest без поля подписи. Происхождение подтверждается
доверенным CI-артефактом/подписью; одной контрольной суммы скачанного файла недостаточно.

**KB-03.** Агент импортирует артефакт релиза через отдельное задание, проверяет подпись или
доверенный канал CI, хеши и совместимость, строит новую ревизию рядом с активной, запускает
проверки и атомарно активирует. Частичный импорт не меняет рабочий индекс. Чтение build-
артефакта позволяет не снимать Basic auth портала stage и не отдавать модели пароль стенда.
Допустим загрузчик с одного разрешённого docs origin при той же проверке manifest;
это транспорт одного механизма импорта, не альтернативный live web search.

**KB-04.** Ревизия связана с установленным релизом. При откате приложения активируется
совместимый manifest. Для rolling deploy нужна явно утверждённая карта совместимости;
модель не выбирает её сама. Несовпадение или неизвестная версия — передача вопроса человеку,
а не инструкции от новой версии. Независимый номер schema не заменяет commit/release.

**KB-05.** Корпус: опубликованные guide/help, проверенные FAQ и известные проблемы.
Фильтр `audience=end_user` действует по умолчанию; self-host/admin статьи добавляются только
для явно соответствующего вопроса. Спецификации, секреты, рабочие документы, дампы,
содержимое комнат и непроверенные разговоры не импортируются. Оператор готовит обезличенный
FAQ из обращения; администратор утверждает его как новую ревизию с источником/сроком действия.

**KB-06.** Язык ответа задаётся явным выбором клиента, иначе последним содержательным
сообщением; при неоднозначности уточняется. `zone` не определяет язык. Ищем сначала в
локали клиента; при недостатке — в другой локали того же manifest. В ответе переводится
объяснение, а ссылки и термины берутся из соответствующей пользовательской локали, если она
есть. Ссылка на другой язык явно обозначается. Для неподдерживаемого языка предложить
RU/EN или человека. Непроверенный машинный перевод не считается опубликованной страницей.

## 5. Harness и инструменты поиска

**RT-01.** Harness — серверный управляющий цикл: обязательные правила, версия промпта,
проверенная личность, ограниченный контекст, разрешённые инструменты, лимиты, журнал решений
и доставка. Для ответа не требуется загружать весь `llms-full.txt` в каждый запрос.
Модель не получает диск, shell, произвольный URL, SQL или API-ключи. MCP для внутренних
двух инструментов не нужен; при будущем внешнем MCP доступ останется таким же ограниченным.

| Инструмент | Принимает от модели | Возвращает |
|---|---|---|
| `knowledge.search` | `query`, желаемый язык, `limit` в пределах сервера | Сниппеты, `doc_id`, `chunk_id`, заголовок, URL, локаль, manifest, признак fallback |
| `knowledge.read` | `doc_id`, разрешённые `chunk_ids` | Ограниченные фрагменты выбранной ревизии с соседним контекстом и ссылками |

`installation`, manifest, аудитория и права берутся из серверного задания и не могут быть
расширены аргументами модели. Query — обычный текст, не выражение для SQL/пути. Чтение
возможно только из доступного корпусного manifest; перебор чужих ID ничего не раскрывает.
Агрегированный контекст получает сам runtime, без модельного выбора `identifier`.

**RT-02.** Разбиение по заголовкам с сохранением инструкций/таблиц; начальный ориентир
400–800 токенов, затем подбор на eval-наборе. FTS учитывает русский/английский и точные
коды ошибок; pgvector даёт смысловой поиск. Слияние и удаление повторов по `doc_id/chunk_id`.
При отказе embeddings разрешён FTS с явной отметкой деградации и теми же проверками ответа;
неподдержанная языковая модель embeddings не подменяется автоматически. Смена embedding-
модели создаёт новый индекс, векторы разных моделей не смешиваются.

**RT-03.** Начальные серверные ограничения: до 6 результатов поиска; до 6 000 токенов
суммарно на тексты инструментов за run; до 3 вызовов knowledge tools и 4 генеративных
вызовов с учётом classifier/summary/judge; вход одного вызова до 12 000 токенов, выход
до 1 000, совокупный input+output всех генеративных вызовов run до 32 000. Более строгий
лимит модели/бюджета имеет приоритет. Служебные схемы инструментов и повторяемая история
тоже учитываются. Для reasoning-моделей требуются ограничение вычислительного вывода и
известный верхний предел тарифицируемого ответа; иначе модель недоступна для auto mode.
Числа — стартовая конфигурация MVP, проверяемая тестами, а не обещание экономии.

**RT-04.** В контексте краткое резюме текущего разговора и последние релевантные сообщения
в пределах лимита. Резюме не переносится между клиентами и не является инструкцией или
источником фактов о продукте. Его генерация учитывается в расходах. Локальный cache хранит
только результаты поиска публичных документов, ключ включает manifest/locale/filters;
персонализированные готовые ответы между пользователями не кешируются.

**RT-05.** Модель возвращает структурированный результат:
`decision=answer|clarify|handoff`, `reply`, `citations[{doc_id,chunk_id}]`,
`category`, `handoff_reason`. Сервер валидирует схему и строит ссылки сам из manifest.
HTML, внешние картинки, произвольные URL и обещания, запрещённые политикой, не отправляются.
Для инструкций проверяется подтверждение существенных утверждений найденными фрагментами;
при неуверенности — уточнение/человек. Существующая ссылка сама по себе не доказывает ответ.
LLM-as-judge допустим как учитываемая дополнительная проверка, не как единственный барьер.
Приветствие, уточнение и передача не требуют фиктивного источника.

## 6. Диалог, надёжная доставка и передача человеку

**CW-01.** При установке зафиксировать Chatwoot version/digest, account/inbox, тип токена
и доступные события. Контрактные тесты должны доказать подпись Agent Bot вебхуков,
отправку public/private сообщений, интерактивную оценку, чтение статуса и CSAT. Не считать
`conversation_status_changed` доступным для Agent Bot без проверки версии; перед отправкой
читать актуальное состояние через API. Неподдержанная версия блокирует auto mode до
обновления или отдельного согласованного адаптера, без снятия проверки подлинности.

**CW-02.** Intake проверяет подпись по raw body, срок подписи (по умолчанию ±5 минут),
account/inbox и размер до 256 KiB. Используются отдельные секреты webhook и Identity
Validation. Входящий непустой `message_created` от клиента создаёт durable job в транзакции;
после commit возвращается 2xx. При недоступной БД — retryable 5xx, не ложное принятие.
Приватные заметки, свои ответы, activity и события оценки не запускают новый AI-ответ.
Независимый сбор метаданных учитывает также ответы людей и все разрешённые разговоры,
в том числе при paused и human-only; отсутствие AI-run не исключает их из качества.
Уникальность включает installation/account/inbox/message/event и при наличии delivery ID.

**CW-03.** На один conversation действует один lease с fencing token; задания упорядочены.
Новые сообщения клиента, пришедшие во время генерации, помечают результат устаревшим:
worker перечитывает историю и объединяет их до следующего ответа в пределах run-бюджета.
При `open`, ручном назначении/ответе сотрудника или отмене бот не отправляет старый ответ.
Последняя API-проверка делается непосредственно перед отправкой; между разными системами
остаётся узкое окно гонки, оно тестируется и журналируется. Нельзя обещать атомарное
исключение гонки без соответствующей поддержки Chatwoot.

**CW-04.** Delivery outbox хранит намерение, ключ результата и полученный Chatwoot message ID.
Повтор входного события не даёт нового намерения. После timeout отправки нельзя слепо
повторять POST: найти уже отправленное сообщение по проверяемой корреляции, доступной
в закреплённой версии Chatwoot. `source_id`/`echo_id` не считать доказанной гарантией
идемпотентности. Если однозначная сверка невозможна, статус `delivery_unknown`, остановка
автоповтора, уведомление оператору и ручное разрешение. Обещается дедупликация собственной
обработки, а не недоказанная exactly-once доставка внешнего API.

**CW-05.** Режимы: `paused` (без LLM), `copilot` (приватное предложение, только человек
отправляет клиенту), `auto` (проверенный публичный ответ). Приватная заметка не является
встроенным approval composer Chatwoot. Переключение в paused запрещает новые model calls
и отправку уже сгенерированных AI-ответов; handoff и уведомление без LLM продолжают работать.
Публикация/откат конфигурации применяется к новым run; текущий закрепляет ревизию, кроме
глобальной паузы, отзыва подключения, ужесточения лимита и ручного захвата разговора.

**CW-06.** Сразу handoff: просьба человека, спорный платёж/возврат, взлом/утечка,
удаление аккаунта/запрос о персональных данных, потеря или несохранение данных, жалоба,
критическая ошибка с техническим контекстом. Нет источника/совместимой версии, timeout,
бюджет, два явно неудачных предложения по одной проблеме — также handoff. Для жалобы
проверить RU/EN формулировки и ошибочные срабатывания. Отсутствие клика не считается неудачей.

Передача: `open`, метка `ai-handoff`, команда support, приватная заметка с сутью, уже
предложенным и причиной, без раскрытия лишних данных. Подтверждение пользователю обещает
ответ в настроенное рабочее время. При отказе Chatwoot передача остаётся незавершённой,
повторяется через outbox и поднимает alert; событие `handoff_completed` возникает только
после подтверждения. Возврат к боту — явное действие сотрудника и актуальный `pending`.

**CW-07.** Агент не закрывает разговор по таймеру молчания. Явное «Да, решена» на вопрос
о результате фиксирует подтверждение клиента и разрешает завершить обращение с заранее
показанным пояснением. Оператор также может закрыть разговор сам, но это отдельный факт
`closed_by_operator`, не доказательство решённой проблемы. Статус `resolved` запускает
штатный CSAT Chatwoot. «Частично»/«Нет» оставляет или возвращает разговор в `open` и
уведомляет человека; ручное закрытие без подтверждения видно как непроверенный результат.
Повторное открытие учитывается отдельно от исходного подтверждения.

## 7. Решение проблемы и удовлетворённость клиента

**FB-01.** Оценивать результат **всей поддержки**, независимо от того, кто отвечал.
Website widget задаёт «Удалось решить вашу проблему?» — «Да, решена» / «Частично» /
«Нет, не решена». Это не рейтинг AI-ответа. Отдельного per-answer голосования в MVP нет.
Рядом постоянно доступно «Позвать человека»; это действие, не отрицательная оценка.

Опрос появляется после предложения решения: сотрудник ставит штатную метку Chatwoot
`solution-proposed`, либо runtime фиксирует содержательное предложение AI. Повтор метки
не создаёт опрос заново. Если оператор сразу закрыл обращение, а опроса ещё не было,
предложить его после закрытия. Одно предложение на эпизод решения, без повторов на каждом
сообщении; после продолжения работы новый эпизод создаётся явно и сохраняет прежний ответ.
При повторном открытии старый положительный результат не переписывается в истории,
но не считается подтверждением результата нового эпизода.

Оценка передаётся интерактивным сообщением Chatwoot. Непрозрачный одноразовый идентификатор
связывает offer с installation/conversation/contact/episode; `submitted_values` не может
выбирать чужое обращение. Сервер сверяет данные через Chatwoot и отправителя-контакта,
принимает только ожидаемые значения. Свободное «да» не превращается в голос. Верификация
личности Remuka обязательна для персонального контекста, но сбор оценки общего обращения
не требует доступа к данным аккаунта. До выбора ясно указать, что «Да, решена» завершает
обращение; «Частично»/«Нет» продолжает работу с человеком.

**FB-02.** Для «Частично»/«Нет» доступны необязательная причина («Не получилось»,
«Решена только часть вопроса», «Проблема повторяется», «Ответ непонятен», «Другое») и
комментарий в Chatwoot. В metrics уходит только код, не свободный текст. Отрицательная
оценка снова открывает даже вручную закрытый разговор и уведомляет support; если человек
уже отвечает, бот не вмешивается. Повторные доставки не создают дублей.
Решение оператора «закрыто» и ответ клиента «решена» хранятся раздельно. В MVP ответ на
опрос эпизода окончательный; исправление/исключение оператором — отдельное аудируемое
действие с причиной, а не замена отрицательной оценки положительной.

**FB-03.** Сохранять `resolution_offered`, `resolution_submitted`, `handoff_requested`
с временем источника/приёма, conversation/episode и причиной. `run_id` и AI-ревизии
опциональны: у human-only обращения их нет. Не подтверждать запись до durable commit;
при сбое восстанавливать событие из проверяемого сообщения Chatwoot. Выбор клиента сам
по себе не запускает LLM. Сбор оценок и их метрик продолжает работать в paused и при
отсутствии подключённого AI-провайдера.

**FB-04.** Второй независимый вопрос — удовлетворённость общением с поддержкой (CSAT).
Его собирает **только штатный Chatwoot** при закрытии обращения. Вторую CSAT-форму не
строить. Поддерживаемую шкалу закрепить адаптером, хранить исходное значение и признак
`positive` (для шкалы 1–5: 4–5). Удовлетворённость и решение проблемы не выводить друг из
друга: клиент может быть доволен общением, хотя проблема ещё существует.

Через API импортировать CSAT и факты отправки опроса, если они доступны. Нельзя полагаться
на наличие CSAT webhook. Сверка каждые 5 минут, пагинация, overlap 24 часа, upsert по
исходному ID; раз в сутки сверять доступное окно retention. Если неизвестно число
отправленных опросов, coverage CSAT — «нет данных», не доля всех закрытых обращений.

**FB-05.** Единица первичного учёта — разговор Chatwoot и его эпизоды, не отдельный ответ.
Для повторного обращения по той же проблеме сотрудник связывает разговоры одного контакта
через команду `link-repeat` в деталях качества; исходные Chatwoot ID сохраняются. Система
не создаёт второй ticket workflow. Автоматическое сходство темы может предложить связь,
но не подтвердить её. Между контактами/установками связывать нельзя; отмена связи
аудируется. Многотемное обращение помечается `multiple_topics`, «Да» означает решение всего
вопроса; частичный результат остаётся частичным. Непоставленная оценка — `unknown`.

## 8. Дашборд качества всей поддержки и система метрик

**QA-01.** `/agent/quality` называется «Качество поддержки». По умолчанию — **все**
разговоры разрешённых inbox: только люди, только AI, совместная работа и ещё без ответа.
AI не обязан участвовать, чтобы обращение вошло в отчёт. Основные фильтры: период,
timezone, зона/среда, inbox, язык, тема, статус. Дополнительный фильтр «Участие AI» и
ревизия/model/provider нужны для анализа причин, но не определяют основные KPI.
Передача от AI к человеку — служебная детализация, не признак плохого решения клиента.

| Показатель | Определение и знаменатель |
|---|---|
| Решение глазами клиента | `yes / (yes + partial + no)` по последнему оценённому эпизоду каждого обращения в выбранной когорте; распределение partial/no/unknown рядом |
| Покрытие подтверждением | Обращения с полученным ответом / обращения с подтверждённо отправленным вопросом о решении |
| Закрыто без подтверждения | Закрытые обращения без ответа клиента о решении; отдельно от подтверждённо решённых |
| CSAT | Положительные / все полученные CSAT; шкала, выборка и coverage при известном числе отправленных опросов |
| Первый содержательный ответ | От первого сообщения клиента до первого публичного содержательного ответа сотрудника или AI, p50/p95; приветствия/опросы/статусы исключены |
| Время до подтверждённого решения | От начала обращения до yes клиента, p50/p95; неподтверждённые и незавершённые не скрываются |
| Время до операционного закрытия | От начала до статуса resolved, p50/p95; не подменяет подтверждение клиента |
| FCR: решение с первого обращения | Подтверждённо решённые при первом обращении, без reopen/связанного повтора 7 суток / все закрытые обращения с полным 7-дневным окном; неизвестный результат не успех |
| Повторные открытия | Разговоры с reopen за 7 суток / закрытые разговоры с полным окном наблюдения |
| Повтор по той же проблеме | Обращения с подтверждённой связью repeat за 7 суток / закрытые обращения с полным окном; полнота ручной разметки показана как ограничение |
| Очередь и просрочки | Открытые/без ответа/ожидающие клиента, возраст p50/p95, число старше целевого рабочего срока |
| Темы и причины неудовлетворённости | Объём, negative/partial, повторы, пробелы знаний и известные проблемы по категориям; есть отдельная категория unknown |

«Обращение» в формулах — исходный разговор, связанные повторы отображаются вместе, но
не удаляются из общего входящего объёма. Количество уникальных проблем — отдельная
группировка по подтверждённым связям, не переименование всех разговоров в уникальные кейсы.
FCR допускает несколько сообщений в первом разговоре и любое сочетание людей/AI.
Это наблюдаемый результат на доступных каналах; неизвестные контакты по другим каналам
не позволяют заявлять абсолютное отсутствие повторных обращений.

Все ratios показывают числитель/знаменатель и unknown. Нет данных — «Нет данных»,
а не 0%/100%; при менее 30 оценках отметка «мало оценок». Опрос о результате и CSAT
считаются отдельно. Первая карточка — решение и удовлетворённость клиента; расходы и
технические метрики агента находятся на другой странице, не подменяют качество поддержки.

По умолчанию последние 7 календарных дней; interval `[from,to)` в timezone установки.
Оценки распределяются по времени ответа на опрос; отдельная когортная вкладка по началу
обращения показывает последнее известное состояние на `as_of`, включая незавершённые.
FCR/repeats — когорта по закрытию с полным 7-дневным окном, число незрелых отдельно.
Времена — по началу соответствующего ожидания; незавершённые показываются с возрастом,
а не теряются при расчёте p95. Рабочее и календарное время разделены; IANA timezone,
расписание/исключения и его ревизия сохраняются. Разница периодов использует одинаковые
определения. Model-фильтр для разговоров означает «с участием модели»; такие срезы могут
пересекаться и не складываются в общий итог. Фильтры в URL не содержат PII.

**QA-02.** Под графиками: нерешённые/частичные, низкий CSAT, повторные обращения,
долгие ожидания и причины. Оператор открывает разрешённое обращение в Chatwoot;
при наличии AI дополнительно видит источники/ревизию/проверки. Аналитик видит агрегаты.
Тексты и PII не копируются в CSV. Можно разобрать противоречивые случаи: высокий CSAT
и нерешённая проблема, низкий CSAT при решении, закрытие без подтверждения.

**QA-03.** Collector работает отдельно от генерации. Он учитывает все разрешённые
conversation/message/status события и сверяет через API метаданные, resolution feedback
и CSAT даже без Agent Bot. Нужный account webhook регистрируется отдельно, если Bot API
не даёт полных событий; это источник того же collector, без второй обработки сообщений.
Дедупликация общая. Исторический backfill метаданных имеет явную границу `coverage_from`;
неизвестное прошлое не восстанавливается выдуманными first-response/status timestamps.

Каталог событий: `support.conversation.created/closed/reopened`,
`support.response.sent {actor_type, substantive}`, `support.resolution.offered/submitted`,
`support.repeat.linked/unlinked`, `support.csat.imported`, `support.handoff.requested/completed`;
дополнительно `support.run.started/finished`, `support.knowledge.activated`,
`support.usage.recorded`, `support.budget.blocked`, `support.configuration.published`,
`support.delivery.unknown`. У события ID, schema version, installation, source/observed
timestamps и минимальные opaque IDs; нет PII/текста/room IDs. `run_id` опционален.
`substantive` для AI задаёт тип результата; для человека исключаются private/activity/
survey и явно маркированные шаблоны подтверждения получения. Неоднозначная классификация
помечается unknown и доступна для аудируемого уточнения, а не угадывается молча.

**QA-04.** В одной транзакции с первичной записью создаётся metrics-outbox. Exporter
at-least-once доставляет в отдельную схему `support` системы метрик (`remo_metrics`, если
она используется), `event_id` unique, отдельная роль. Не менять знаменатели продуктовых
метрик и не выдавать поддержку за `agent.task.finished`/MAU. Миграция и каталог поставляются
с сервисом. Дашборд использует ту же модель событий в локальной проекции и продолжает
работать при отказе sink; после восстановления итоги совпадают. Клиентский analytics JS
не нужен. При отсутствии sink события сохраняются локально с видимым статусом; подключение
системы метрик и проверка human-only обращений входят в облачную приёмку.

## 9. Токены, стоимость и бюджеты

**BU-01.** `/agent/usage`: день/неделя/месяц/произвольный период `[from,to)`, timezone,
installation, provider connection, requested/actual model, операция, режим и ревизия.
Итоги: запросы/ошибки/повторы, input/output, cached input, reasoning, embedding tokens,
оценённая/сверенная стоимость, неизвестные суммы и открытые резервы. Разбивка по времени,
провайдеру, модели и операции; топ дорогих run доступен администратору. CSV с теми же
фильтрами и правами, защитой от formula injection, без ключей и содержимого обращений.
В сводке затрат показывать и накопленные счётчики токенов, и стоимость за период.

**BU-02.** На каждую реальную попытку провайдера: `attempt_id`, `run_id?`, `job_id`,
`operation=classify|generate|summarize|judge|embed_query|embed_index|eval|connection_test`,
provider connection, requested/actual model, provider request ID, start/end/status,
config/price revision, input/output/cached/reasoning/embedding usage, `usage_source`,
`cost_state=estimated|reconciled|unknown`, currency, сумма decimal и ссылка на raw usage
без текста. Cached input обычно является частью input, reasoning может быть частью output:
адаптер нормализует по документации провайдера и тестируется на отсутствие двойного счёта.
Общая генеративная сумма = input+output без повторного прибавления их подкатегорий;
embeddings показываются отдельно, вместе складываются только как подписанный «все операции».

Индексация, поиск с embedding API, тесты подключения, eval, повторы, неудачные оплаченные
вызовы и fallback входят в расходы. Нет `run_id` у индексации — это не причина потерять
расход. Переход на фактическую модель провайдера не может незаметно выбрать другой тариф:
недокументированное расхождение блокирует следующие auto calls до проверки подключения.

**BU-03.** Тариф — версионированные ставки за категории токенов/запросы/хранение, валюта,
единица тарификации, дата действия и источник. Модель не придумывает цену. Историческая
запись закрепляет тариф; его изменение не пересчитывает историю молча. Денежные значения
не считать float. Корректировки — отдельные записи с причиной, не уничтожение первичной
оценки. Суммы разных валют показываются раздельно; общий итог в выбранной валюте возможен
только с опубликованной ревизией FX-курсов/датой, без неё — «общий денежный итог недоступен».

**BU-04.** Usage брать из ответа API. При timeout/отсутствии usage сохранять `unknown`,
предварительную верхнюю оценку и резерв; не писать ноль. Периодическая сверка с usage API
провайдера или импортом отчёта администратора сохраняет происхождение корректировки.
Если запросы нельзя сопоставить, держать нераспределённую корректировку provider/period,
не выдумывать точную стоимость разговоров. Неразрешённые случаи требуют решения
администратора с аудитом; такой резерв не освобождается просто по истечении lease задания.
Расходы группируются по времени попытки; поздняя корректировка меняет соответствующий
период и `as_of`, выгрузка указывает время расчёта и долю сверенных сумм.

**BU-05.** Лимиты: токены/стоимость на разговор, вызовы на run, денежный суточный и месячный
лимит установки, подлимит provider connection, отдельный подлимит indexing/eval. Все операции
участвуют в общем лимите; служебное задание не обходит его. Месячный период календарный,
границы в timezone установки, UTC хранится в БД. В MVP только per-installation бюджеты;
единый hard cap RU+EU не обещается без общего координатора.

До каждого вызова атомарно резервировать консервативную верхнюю стоимость входа, разрешённого
выхода, reasoning и платных инструментов. Проверка включает уже потраченное и все активные
резервы соответствующих периодов; одна транзакция проверяет все вложенные лимиты. Если
период меняется до dispatch, резерв переносится атомарно до отправки. Контекст и выход
реально ограничиваются адаптером. Неполный тариф/неизвестный верхний предел блокирует auto
для этого подключения. Для eval/test тоже нужен явный ограниченный бюджет.

После ответа записывается фактический usage и остаток резерва освобождается. Timeout
сохраняет возможный расход; retry — новая попытка с новым резервом. При исчерпании
лимита — передача человеку без дополнительного LLM-вызова. Пороги предупреждения 50/80/100%
настраиваются; стартовые значения пример конфигурации, не разрешение на расходы. Любое
повышение лимита администратором аудируется. Provider-side spending cap настраивается
дополнительно; финальная сумма счёта может отличаться из-за внешних тарифов/задержек.

**BU-06.** Расходы на модели в расчёте на решённое обращение: все model-затраты зрелой
когорты / число её подтверждённо решённых обращений; при нуле — «не рассчитывается».
Отдельно видны затраты на все обращения и срезы по участию AI. Это не полная себестоимость
поддержки: зарплата, инфраструктура и время человека в сумму model calls не входят.
Общие indexing/eval затраты показываются отдельно с описанным методом распределения,
если он включён. Ретраи и неуспешные разговоры нельзя исключать ради красивой стоимости.
Для смешанной валюты сначала применяются правила BU-03. Финансовая метрика не заменяет
решение проблемы и CSAT на странице качества.

| Страница | Обязательные состояния и действия |

| `/agent/quality` | Качество всей поддержки по §8, включая human-only; причины, фильтры, пусто/загрузка/ошибка/устаревший импорт, переход в Chatwoot |
| `/agent/usage` | Метрики §9, известные/неизвестные суммы, бюджеты, резервы, тарифы, CSV |
| `/agent/knowledge` | Manifest/релиз/языки, полнота, проверка поиска, история импортов, ошибки, активация/откат администратором |
| `/agent/settings` | Режим, промпт, подключения/модели, лимиты, расписание, предупреждения, ревизии, тест/публикация/откат |

**UI-01.** RU/EN, клавиатура, явные labels и ошибки, видимый focus, доступный контраст,
адаптация 390/1440 px. UI использует опубликованные Remuka tokens или версионированный
экспорт пакета UI, не копию произвольных цветов. До реализации подготовить утверждённые
макеты всех четырёх страниц, light/dark и основных состояний. Действует ADR-286: приёмка
рядом с макетом; существующие `docs/design/mockups/` агентами не редактируются.

**CFG-01.** Промпт: системные правила безопасности неизменяемы в image; редактируется
инструкция о тоне/порядке объяснения и разрешённые настройки. В панели видны обе части и
их граница, SHA/revision. Редактор не позволяет вставлять секреты/инструменты или отменять
правила доступа; ограничения всё равно применяются кодом независимо от текста промпта.

**CFG-02.** Подключение: имя, тип адаптера, HTTPS base URL из разрешённого инфраструктурой
списка, secret (write-only), допустимые model IDs, регион/политика данных, таймауты и тариф.
Поддержать OpenAI-compatible и отдельный нативный адаптер второго выбранного провайдера;
совместимый URL не гарантирует совместимость usage/tools/reasoning. Возможности каждого
проверяет capability test. Полный тест приёмки обязан пройти на двух адаптерах с fixture-
сервером; реальные подключения разрешаются после региональной и эксплуатационной проверки.
Конкретные оплачиваемые модели выбирает администратор, в ТЗ нет вечного «лучшего model ID».

Ключ можно заменить/отозвать, прочитать обратно нельзя. Шифрование authenticated encryption,
KEK/key ID вне БД и образа; ротация с повторным шифрованием и проверкой восстановления.
Сетевой allowlist управляется инфраструктурой, не обычным оператором; приватные адреса,
redirect и DNS rebinding блокируются. При необходимости внутреннего gateway — отдельное
инфраструктурно утверждённое исключение, без отключения общей защиты outbound.

**CFG-03.** Цикл: создать draft → проверить подключения/индекс/тарифы → запустить ограниченный
eval → diff с активной версией → publish с причиной. Конкурирующая правка получает conflict
по version/ETag, не теряет изменения другого администратора. Опубликованная ревизия
неизменяема; rollback создаёт новую активацию предыдущей конфигурации после повторной
проверки зависимостей/секретов/цены. Ошибка проверки сохраняет предыдущую активную версию.
Обычные изменения действуют без restart, видна дата/автор и число run на каждой ревизии.

**CFG-04.** Только администратор публикует, возобновляет auto и добавляет fallback-маршрут.
Fallback выключен по умолчанию; включённый маршрут должен иметь свой проверенный адаптер,
регион и тариф и проходить новый бюджетный резерв. Тихий переход к более дорогой модели
или другой зоне запрещён. Отзыв секрета/подключения и пауза немедленно блокируют новые
dispatch; незавершённые ответы не уходят клиенту. Разговор передаётся человеку без LLM.

## 11. Данные, API и аудит

Логические сущности отдельной БД: installations; operator sessions/role mapping;
provider_connections и encrypted_secret_versions; immutable config/prompt/price revisions;
knowledge manifests/documents/chunks/embeddings; jobs/leases; runs/tool calls;
delivery_outbox/reconciliation; feedback offers/responses; CSAT projection;
decision_events/metrics_outbox; usage_attempts/cost_adjustments/budget_reservations;
audit и dashboard projections. Первичные связи содержат installation; cross-installation
reference запрещён внешними ключами/проверками. Runtime DML-role не владеет таблицами;
миграции выполняются отдельной ролью. Индексы и события не зависят от product DB.

| Контракт | Доступ и результат |
|---|---|
| `POST /agent/webhooks/chatwoot` | Только подписанный отправитель, bounded intake; без операторской cookie |
| `/agent/auth/*` | Единственный OIDC flow, защищённая серверная сессия |
| `/agent/api/v1/quality`, `/usage` | Серверный RBAC и фильтры по разрешённой установке; определения метрик в ответе |
| `/agent/api/v1/configurations/*` | Draft/test/publish/rollback, CSRF, версии, отдельные команды с аудитом |
| `/agent/api/v1/connections/*`, `/knowledge/*` | RBAC, secret write-only, ограниченный test/import, аудит |
| `/health/live`, `/health/ready`, `/metrics` | Только внутренняя сеть/аутентифицированный мониторинг; без конфигурации и секретов |

Предоставить OpenAPI и JSON schemas событий/инструментов. Для каждой мутации — единая
command-служба с проверкой прав, аудитом и идемпотентностью там, где команда повторяется.
GET не меняет конфигурацию. Аудит: actor, installation, время, операция, версии до/после,
причина; маскировать secret/body. Чтение индивидуальных решений, экспорт и вызов контекста
Remuka тоже аудируются. Скрытые chain-of-thought не сохраняются; нужен краткий код причины,
источники и результаты проверок, а не внутренние рассуждения модели.

## 12. Безопасность, регионы и хранение

**SEC-01.** Текст клиента, документы и вложения — недоверенные данные. Разделять их
с системными инструкциями; проверять параметры инструментов и права вне модели. Вложения
в MVP не передавать модели автоматически: оператор читает их в Chatwoot. Не ходить по
ссылкам клиента. Удалять лишние персональные данные из контекста модели, но не объявлять
маскирование гарантией анонимности. Никогда не просить пароль, одноразовый код или карту.

**SEC-02.** Для персонального контекста использовать verified support identifier из
проверенного contact/inbox, подтверждённого API Chatwoot. Поля custom attributes, email
или ID из текста не дают полномочий. Контекст только минимальный по §2.5 `support.md`,
без room content и сведений о посторонних организациях. Технический контекст — только с
согласием клиента по исходному контракту; отсутствие согласия не мешает общей помощи.
Если агрегированный API даёт больше полей, чем нужно вопросу, модель получает allowlist.

**SEC-03.** Четыре независимые установки stage-ru/stage-eu/prod-ru/prod-eu: отдельные
DB/credentials, очереди, Chatwoot inbox, feedback и provider projects. Маршрут модели
публикуется только для одобренной зоны. Даже одинаковый публичный корпус не разрешает
объединять историю клиентов. Централизованный обзор возможен только по обезличенным
агрегатам без conversation/contact IDs. География VPS сама по себе не доказывает
соответствие обработке персональных данных: провайдеры/политики хранения утверждаются
владельцем до включения реальных данных. Stage использует синтетические обращения.

**SEC-04.** Ретенция по умолчанию: сырые зашифрованные webhook payload для воспроизведения
до 24 часов; временная история/контекст run удаляется не позднее 24 часов после завершения;
метаданные решений, feedback, usage и аудит — 365 дней; обезличенные месячные агрегаты —
24 месяца. Тексты хранятся в Chatwoot по его отдельно утверждённой политике, здесь не
дублируются. Активные incident/legal holds и неразрешённые денежные корректировки
защищаются от удаления с причиной и сроком пересмотра. Технические JSON-логи — 14 дней,
без содержимого сообщений и токенов. Backups — ежедневные, 14 копий, шифрование и отдельный
доступ; сроки согласовать с политикой оператора до production. Эти числа — defaults,
изменения политики аудируются и не снимают обязательные hold.

Оставлять активные и используемые конфигурации/manifest, версии, нужные для сохранённых
решений, и версии, доступные для rollback. Остальные индексные данные могут пересобираться
из сохранённых доверенных артефактов. Retention job сначала формирует dry-run перечень
ссылок/hold, затем выполняет установленную политику; это будущая функция, данное ТЗ
не разрешает очистку текущих VPS или рабочих файлов. Удаление персональных ссылок по
законному запросу оставляет только действительно обезличенные агрегаты; отдельно учесть
backups и процедуру повторного удаления при восстановлении.

## 13. Эксплуатационные и технические требования

**OPS-01.** Compose-развёртывание по commit/image digest, env.example без секретов,
отдельный install/migrate/check/deploy/rollback/backup/restore runbook. Bootstrap env:
installation/zone/environment, DB URLs runtime/migrator, OIDC issuer/client secret и role
mapping, KEK/key ID, внутренние origins/allowlists, Chatwoot integration credentials,
metrics sink. Промпт/model/тариф/budget не дублируются в env после bootstrap: источник
настроек один — опубликованная конфигурация. Секреты на диске mode 600, не в git/образе.

**OPS-02.** На существующем support host новые маршруты `/agent/` и webhook направляются
в новый сервис; `/app`, `/widget.html`, Chatwoot API/SDK/websocket и origin validation
сохраняются. Не менять настроенные домены/сертификаты или снимать защиту со всей stage-
зоны ради webhook. Webhook доступен Chatwoot без Basic auth, защищён подписью; операторская
страница на stage остаётся за ограничением стенда и OIDC. Проверить path precedence,
CSP, proxy timeouts и websocket отдельно. Нового публичного поддомена для MVP не требуется.

**OPS-03.** Начальный профиль — 2 одновременных разговора и один worker индексации только
вне пика; глобальный semaphore не даёт индексации вытеснять ответы. Ресурсная цель новых
API+worker процессов: суммарный RSS до 512 MiB в steady state, до 768 MiB при импорте,
до 1 vCPU; без локальной LLM/embedding-модели. PostgreSQL имеет отдельный согласованный
лимит: RAM его общего процесса нельзя честно приписать одному сервису по RSS. До stage-
установки замерить оставшийся запас VPS с уже работающими Remuka/Chatwoot; при нехватке
уменьшить concurrency/перенести сервис, не отнимать память у существующих контейнеров.
Ограничить пул БД 5 соединениями на процесс. Это цели нагрузочной проверки, не замеры VPS.

**OPS-04.** На контрольном корпусе до 2 000 фрагментов и 2 concurrent conversations:
webhook durable ack p95 ≤1 с, поиск p95 ≤500 мс без времени внешнего embedding API,
первый содержательный ответ p95 ≤30 с при ответе провайдера ≤20 с. End-to-end deadline
run 45 с, дальнейшая работа прекращается и запускается handoff. До dispatch проверяется
возраст задания; старше 60 с — handoff вместо запоздалой генерации. Несодержательные
автоуведомления не подменяют первый ответ. Если условия не достигнуты, приложить профиль
и изменить capacity до production; не заявлять SLA по одному успешному запросу.

**OPS-05.** Timeout/retry с backoff и jitter, учитывать 429/Retry-After; максимум две
попытки генерации в пределах общего deadline и бюджета. Non-idempotent delivery — только
по CW-04. Graceful shutdown прекращает intake/dispatch, освобождает только безопасные
lease, не забывает usage exposure; restart восстанавливает очередь/outbox/резервы.
`ready` проверяет БД/миграции и возможность обработки; состояние paused или отсутствие
активного индекса видно как business state, не бесконечный crash/restart. Отказ агента
не мешает ручным ответам Chatwoot; alert по отсутствию heartbeat и зависшим pending.

**OPS-06.** JSON logs/trace ID без PII; OpenTelemetry-compatible HTTP/model/tool spans,
provider/model, latency, error type и token usage. Зафиксировать версию GenAI semantic
conventions при реализации; стоимость вести своим ledger, не приписывать OTel универсальную
финансовую семантику. Метрики с низкой кардинальностью: никаких contact/conversation ID
в Prometheus labels. Alert: очередь >30 с, доставка unknown, незавершённая передача,
ошибки провайдера, неактуальный manifest, бюджет, отставание CSAT/metrics >15 минут.
Уведомления имеют дедупликацию и не содержат текста обращения; канал задаётся при установке.

**OPS-07.** Бэкап до миграции; expand/contract миграции, проверка схемы до старта worker.
KEK резервируется отдельно от БД, восстановление секрета проверяется тестовым подключением.
Цели MVP: RPO ≤24 ч для локальных метаданных, RTO ≤2 ч на восстановлении в чистую stage-БД;
Chatwoot имеет собственный бэкап. Нельзя обещать сквозной RPO переписки только бэкапом
агента. После restore — сверка Chatwoot, provider exposure и outbox до auto mode;
не переотправлять все старые ответы автоматически. Runbook обязателен в комплекте сервиса.

| A05 | Найти точный код и перефразированный вопрос | FTS и semantic fixtures находят ожидаемые фрагменты; tool/context budgets соблюдены |
| A06 | Попросить чужой файл/комнату/URL, внедрить инструкции в статью | Никакого чтения/исходящего запроса/раскрытия за пределами tools и allowlist |
| A07 | Подделать webhook, replay, account/inbox | Отказ до задания; повтор правильного события не создаёт второго результата |
| A08 | Перезапуск после commit intake и после provider call | Задание не теряется, usage учитывается, оплаченный вызов не забывается |
| A09 | Chatwoot принял POST, но ответ сети потерян | Сверка находит сообщение; либо delivery_unknown и ручное разрешение без слепого дубля |
| A10 | Оператор отвечает во время генерации, меняет pending/open | Устаревший ответ отменён при наблюдаемом захвате; остаточная гонка описана и проверена |
| A11 | Клиент просит человека/возврат/сообщает потерю данных | Handoff с заметкой и подтверждением, auto прекращён, источник не выдуман |
| A12 | Нет источника, provider timeout, бюджет исчерпан | Честная передача без лишнего LLM, Chatwoot остаётся пригоден для человека |
| A13 | Пользователь выбирает Решена/Частично/Нет или просит человека | Верная привязка к conversation/episode; partial/no открывает работу, handoff не подменяет оценку |
| A14 | Повтор/подмена feedback, свободный текст «да» | Нет дубля и чужой оценки, текст не превращён в голос |
| A15 | Завершение, native CSAT и reopen | CSAT импортирован один раз, шкала сохранена, reopen не считается AI-успехом |
| A16 | Отключить CSAT webhook/факт отправки опроса | API-сверка восстанавливает оценки; неизвестный denominator обозначен, не выдуман |
| A17 | Fixture: 10 обращений с offered, yes=3, partial=1, no=1, unknown=5 | Подтверждение решения=60% среди ответивших, coverage=50%; неизвестные не успех; пусто — «Нет данных» |
| A18 | Fixture: 4 CSAT [5,4,2,1], 8 sent surveys | CSAT=50%, coverage=50%; высокий CSAT не подменяет подтверждение решения |
| A19 | Разговор с двумя моделями и человеком | Одна оценка результата обращения; AI=mixed только фильтр, нет двойного суммирования и рейтинга отдельного AI-ответа |
| A20 | Usage fixtures cached/reasoning, retry, embed/index/eval | Точные итоги по моделям/провайдерам/периоду; подкатегории не добавлены дважды |
| A21 | Timeout с неизвестным usage и поздняя корректировка | Unknown не равен нулю; резерв не освобождён; история цены/корректировки сохранена |
| A22 | Два concurrent calls конкурируют за один остаток | Зарезервирована только допустимая сумма; сумма spent+reserved соблюдает лимит |
| A23 | Полночь/месяц/DST, новый тариф и разные валюты | Верные периоды/ревизии; без FX нет выдуманного общего денежного итога |
| A24 | Правка промпта/model/connection и publish из браузера | Новый run на новой ревизии без restart; старый закреплён; secret нельзя прочитать |
| A25 | Попытка ослабить policy, дорогой/чужой fallback | Код блокирует обход; права/регион/тариф проверены до dispatch |
| A26 | Откат при отозванном ключе, конфликт двух drafts | Явная ошибка/409, активная версия не сломана; успешный rollback аудируется |
| A27 | Роли analyst/operator/admin, неверный OIDC/CSRF | Сервер отказывает запрещённым операциям и полям, CSV соблюдает те же права |
| A28 | Пауза при генерации и отрицательная оценка после неё | Новый LLM/public AI send заблокирован; feedback/handoff всё ещё записываются |
| A29 | Отключить metrics sink на 20 минут | Локальные оценки не теряются; после retry нет дублей, внешние итоги совпали |
| A30 | Обход панелей RU/EN, 390/1440, light/dark и клавиатура | Скриншоты с макетом, loading/empty/error/stale состояния, доступность |
| A31 | Сеть RU/EU/stage/prod, поддельный contact/context | Нет пересечения данных/ключей и доступа по клиентским атрибутам |
| A32 | Нагрузка OPS-03/04 и отказ embeddings | Протокол RSS/latency/queue, безопасная деградация; не нарушена работа Chatwoot |
| A33 | Restore в чистую stage-БД | Выполнены RPO/RTO, расшифровка, outbox/usage reconciliation до auto |
| A34 | Добавить `/agent/` на stage ingress | `/app`, widget, API и websocket продолжают работать; ограничения stage сохранены |
| A35 | Retention dry-run и запрос удаления | Защищены references/holds; тексты/PII отсутствуют в метриках, restore учитывает удаления |
| A36 | AI выключен; человек предлагает решение и закрывает разговор | Опрос результата/CSAT/время/очередь и metrics export работают без единого AI-run |
| A37 | Клиент подтвердил решение, затем reopen/новое связанное обращение; оператор закрыл другое без ответа | FCR и повторы верны на зрелой когорте; закрытие/молчание не считаются подтверждённым решением |

Eval-набор: минимум 100 синтетических/обезличенных случаев, не менее 40 на каждом RU/EN;
включить уточнения, отсутствие ответа, ошибочные источники, передачу, prompt injection,
поддельную идентичность, разные версии и смешанный язык. Набор делится на разработческий
и отложенный; все обязательные handoff/security cases проходят, не менее 90% ответимых
отложенных случаев имеют правильные существенные утверждения и подходящие источники
по ручной рубрике. Отчёт содержит число случаев, ревизии, стоимость и ошибки, не только %.
Это ограниченный release gate, не доказательство отсутствия всех уязвимостей и не замена
полевым метрикам. 50% автоматизации и 70% положительных оценок из старого ТЗ остаются
гипотезами для наблюдения; по ним нельзя объявлять реализацию принятой.

## 16. Условия включения и передача в разработку

До stage задать: OIDC/роли, закреплённую версию Chatwoot, origin/inbox и секреты, доверенный
канал manifest, поддерживаемый PostgreSQL+pgvector, approved model connections, тарифы,
явные денежные лимиты, timezone/часы, metrics sink и alert destination. Значения секретов
и реальные счета не вписываются в ТЗ. Default установки — paused, без разрешённых платных
вызовов; настройка бюджета означает разрешение только в его пределах.

До production: утверждённые политики данных и retention для каждой зоны, проверенные
макеты/приёмка A01–A37, восстановление, отчёт eval, результаты ограниченного пилота и
контакт ответственного. Не подтверждённые инфраструктурные предпосылки отмечаются в
deployment checklist, а не выдаются за уже настроенные. Развёртывание сервиса, платные
вызовы, изменения VPS и публикация репозитория — отдельные действия после реализации;
данная задача создаёт документы и не выполняет их.

## 17. Основания решений

Первичные источники проверены 2026-11-24. Ссылки описывают возможности и подходы;
пороговые значения, схемы и бюджетные правила выше — требования этого проекта.

- [Chatwoot Agent Bot](https://www.chatwoot.com/hc/user-guide/articles/1677497472-how-to-use-agent-bots): внешняя логика бота и передача pending/open.
- [Chatwoot webhooks](https://www.chatwoot.com/hc/user-guide/articles/1677693021-how-to-use-webhooks): проверка подлинности и различия доступных событий.
- [Chatwoot interactive messages](https://app.chatwoot.com/hc/user-guide/articles/1677689344-how-to-use-interactive-messages): варианты ответа в Website widget.
- [Chatwoot CSAT](https://app.chatwoot.com/hc/user-guide/articles/1677693868-how-to-read-csat-reports): оценка удовлетворённости и доля ответивших.
- [Anthropic: context engineering](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents): получение нужного контекста инструментами по мере необходимости.
- [OpenAI file search](https://developers.openai.com/api/docs/guides/tools-file-search): пример управляемого поиска по загруженным материалам; это рассмотренная альтернатива, не выбранный backend MVP.
- [OpenTelemetry GenAI](https://opentelemetry.io/docs/specs/semconv/gen-ai/): соглашения наблюдаемости; версию и актуальный путь зафиксировать при реализации.
- [OWASP: prompt injection prevention](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html): ограничения инструментов и проверки вне модели.
