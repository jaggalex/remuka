# Двухфакторный вход (TOTP) для операторов

ТЗ к **ADR-260**. Статус: этапы 1–2 и проверки `/operator/*` реализованы, 2026-11-23; письма — этап 4. Нужен до этапа 3 `spec/operator.md`
(действия с деньгами в консоли). Прежде чем менять код, прочитайте `AGENTS.md`, ADR-094,
ADR-178, `spec/IAM-v1.md` (сессии и вход), `spec/mail.md`, `spec/operator.md`,
`apps/sync/secrets.mjs` (KEK).

## 0. Зачем и что в объёме

Учётная запись оператора даёт доступ к возвратам, кредитам, данным клиентов и мерам по
жалобам. Сейчас её защищает только пароль. Утечка пароля или почты не должна давать доступ к
консоли.

**В объёме:**

1. TOTP по RFC 6238 — коды из приложения-аутентификатора (Яндекс Ключ, Google Authenticator,
   1Password, Bitwarden и другие).
2. Обязателен для всех с ролью оператора; для остальных пользователей в этом ТЗ недоступен, но
   устройство это позволяет (§9).
3. Второй шаг при входе, подтверждение перед изменяющими действиями, резервные коды,
   сброс только с сервера, уведомления письмом.

**Вне объёма:** passkeys и ключи WebAuthn, SMS (небезопасно и платно), 2FA для клиентов и
политика «обязательно для администраторов организации» — следующим шагом (§9).

## 1. Правила

1. **Без второго фактора операторская консоль не открывается.** Роль, выданная
   `operator:grant`, начинает работать в интерфейсе только после подключения TOTP. Команды на
   сервере (CLI) второй фактор не требуют: доступ к серверу — корень доверия (`spec/operator.md`
   §1.1).
2. **Сброс второго фактора — только с сервера.** Никакого «потерял телефон — пришлём письмо»:
   иначе взлом почты обходит защиту.
3. **Секрет хранится зашифрованным** ключом KEK (`encryptSecret`, как ключи провайдеров ИИ) и
   никогда не возвращается клиенту после подключения.
4. **Один код — один раз.** Повтор уже принятого кода отклоняется, даже в пределах его 30 секунд.
5. **Каждое событие — строка аудита и письмо** владельцу аккаунта (§7).
6. **Без внешних сервисов.** QR-код рисуется в браузере библиотекой из репозитория; секрет не
   уходит на сторонние сайты.

## 2. Параметры TOTP

- Алгоритм SHA-1, 6 цифр, шаг 30 секунд — то, что поддерживают все приложения.
- Секрет — 20 случайных байт (`crypto.randomBytes`), в интерфейсе — Base32.
- Окно проверки: текущий шаг и по одному соседнему (±30 с) на рассинхронизацию часов.
- Сравнение — за постоянное время (`crypto.timingSafeEqual`).
- `otpauth://totp/<issuer>:<email>?secret=…&issuer=<issuer>&algorithm=SHA1&digits=6&period=30`.
- **`issuer` различает установки:** «Ремука (РФ)» на `app.remuka.ru`, «Remuka (EU)» на
  `app.remuka.com`, `REMO_PRODUCT_NAME` — на self-host. У оператора двух установок в
  приложении две разные записи, и их нельзя перепутать.
- Часы серверов синхронизированы (chrony или systemd-timesyncd). Метрика
  `remo_mfa_clock_skew_rejects_total` — коды, которые подошли бы при сдвиге на 2–3 шага; её
  рост — сигнал проверить время на сервере.

## 3. Данные

```sql
create table user_mfa (
  user_id uuid primary key references users (id) on delete cascade,
  kind text not null default 'totp' check (kind = 'totp'),
  secret_ciphertext bytea not null,     -- encryptSecret, scope 'mfa', scopeId = user_id
  secret_nonce bytea not null,
  kek_id text not null,
  confirmed_at timestamptz,             -- null: подключение начато, но не подтверждено
  last_step bigint,                     -- номер последнего принятого шага (правило 4)
  created_at timestamptz not null default now()
);

create table user_mfa_recovery_codes (
  user_id uuid not null references users (id) on delete cascade,
  code_hash bytea not null,             -- SHA-256: у кода 50 бит случайности
  used_at timestamptz,
  primary key (user_id, code_hash)
);

create table mfa_challenges (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users (id) on delete cascade,
  token_hash bytea not null unique,
  purpose text not null check (purpose in ('login', 'step_up')),
  attempts integer not null default 0,
  expires_at timestamptz not null,      -- 5 минут
  created_at timestamptz not null default now()
);

alter table sessions add column mfa_at timestamptz;   -- когда в этой сессии последний раз введён код
```

- RLS — как у `sessions`: строка видна только своему аккаунту. Оператор чужие строки не читает.
- Неподтверждённая запись `user_mfa` старше 1 часа удаляется задачей очистки.
- Строки этих таблиц описаны в `spec/account-deletion.md` §3 (удаляются вместе с аккаунтом), и
  тест ссылок на `users` это проверяет.

## 4. Подключение

Настройки аккаунта → «Безопасность» → «Двухфакторный вход». Для оператора без TOTP
`/operator` ведёт сюда с пояснением.

1. Ввести пароль (подтверждение личности).
2. Сервер создаёт секрет, сохраняет неподтверждённую запись и один раз возвращает `otpauth://`
   и Base32. Клиент рисует QR и показывает ключ текстом для ручного ввода.
3. Человек вводит код из приложения. Верный — `confirmed_at = now()`, `last_step` записан.
4. Сервер выдаёт **10 резервных кодов** формата `XXXXX-XXXXX` (Base32, без похожих символов),
   показывает один раз. Кнопки «Скачать .txt» и «Скопировать». Продолжить можно только после
   отметки «Я сохранил коды».
5. Все прочие сессии аккаунта завершаются; текущая получает `mfa_at = now()`. Письмо «Включён
   двухфакторный вход».

Повторная генерация резервных кодов — в том же разделе, с вводом кода TOTP; старые коды
перестают работать.

## 5. Вход

1. `POST /auth/login` с e-mail и паролем — как сейчас, с тем же ограничением попыток. Если у
   аккаунта есть подтверждённый TOTP, сессия **не** создаётся. Ответ:
   `202 { mfaRequired: true, challenge: "<токен>" }` (сессия ещё не создана). В базе —
   `mfa_challenges` с хешем токена, `purpose = 'login'`.
2. Экран «Код из приложения»: поле на 6 цифр с `autocomplete="one-time-code"`, ссылка
   «Использовать резервный код».
3. `POST /auth/login/mfa { challenge, code }` или `{ challenge, recoveryCode }`:
   - верно — сессия как обычно, с `mfa_at = now()`; вызов удалён;
   - неверно — `attempts + 1`; после 5 попыток вызов удаляется, нужно снова ввести пароль;
   - на аккаунт — не больше 10 неверных кодов за час, потом вход по коду закрыт на час и
     уходит письмо «Много неверных кодов».
4. Резервный код помечается `used_at`; письмо «Использован резервный код, осталось N». При
   остатке меньше 3 — подсказка в интерфейсе сгенерировать новые.
5. Ответы на неверный пароль и на неверный код различимы только после верного пароля: до этого
   по ответу нельзя узнать, включён ли у аккаунта второй фактор.

## 6. Подтверждение перед действиями (step-up)

Заменяет «повторный ввод пароля» из `spec/operator.md` правило 6 для аккаунтов с TOTP.

- Все маршруты `/operator/*` требуют сессию с `mfa_at` не старше **12 часов**. Иначе
  `403 MFA_REQUIRED` — консоль показывает окно ввода кода.
- Изменяющие маршруты `/operator/*` (возврат, кредит, тариф, меры по жалобам) требуют `mfa_at`
  не старше **15 минут**.
- `POST /operator/session/confirm { challenge, code }` проверяет код и обновляет `mfa_at`
  текущей сессии; `challenge` — из ответа `403 MFA_REQUIRED`. Отдельного `/auth/step-up`
  нет: это тот же механизм, что и второй шаг входа (§5). Ограничения попыток — как в §5.
- Чтение (Пульс, карточка клиента, журнал) не требует свежего кода в пределах 12 часов.

## 7. Сброс, отключение, уведомления

- **Сброс с сервера:** `pnpm mfa:reset --email <адрес> --reason "..." --as <оператор>`.
  Удаляет секрет и
  резервные коды, завершает все сессии, пишет аудит, шлёт письмо «Двухфакторный вход сброшен
  с сервера». Следующий вход в консоль снова потребует подключения. `--as` — автор команды,
  как у остальных операторских команд (поправка ADR-259).
- **Отключить TOTP самому** оператор не может, пока у него есть роль: сначала
  `operator:revoke` на сервере. Для будущих пользователей без роли — отключение с вводом кода
  (§9).
- **Письма** (шаблоны в `mail-templates.mjs`, RU/EN, адреса поддержки — по зоне,
  `spec/account-deletion.md` §4):

| Событие | Письмо | Аудит |
| --- | --- | --- |
| Подключение | «Включён двухфакторный вход» | `mfa.enabled` |
| Новые резервные коды | «Резервные коды обновлены» | `mfa.recovery_regenerated` |
| Вход резервным кодом | «Использован резервный код, осталось N» | `mfa.recovery_used` |
| 10 неверных кодов за час | «Много неверных кодов» | `mfa.locked` |
| Сброс с сервера | «Двухфакторный вход сброшен с сервера» | `mfa.reset` |

В каждом письме: время, примерное место по IP не указывается (нет геолокации), строка «Если
это были не вы — напишите на security@remuka.com».

## 8. Интерфейс

- Экраны на `@remo/ui`: подключение (QR, ключ, поле кода, резервные коды), второй шаг входа,
  окно подтверждения в консоли.
- QR — небольшая библиотека из npm в составе сборки (не CDN, CSP не меняется). Новая
  зависимость проходит `pnpm audit:prod` и проверку лицензии.
- Тексты в i18n RU/EN; в поле кода — только цифры, вставка кода с пробелом работает.
- Доступность: поле кода с `<label>`, ошибки через `aria-describedby`, QR с текстовой
  альтернативой — ключом для ручного ввода.

## 9. Что дальше (не в этом ТЗ)

- 2FA по желанию для любого пользователя — тот же механизм, раздел «Безопасность» открыт всем.
- Политика организации «двухфакторный вход обязателен для администраторов».
- Passkeys как второй фактор и как вход без пароля.

## 10. Этапы

1. Таблицы, шифрование секрета, проверка кода по RFC 6238 с защитой от повтора, `mfa:reset`.
   *Сделано: `user_mfa`, `user_mfa_recovery_codes`, `mfa_challenges`, `sessions.mfa_at`
   (схема 35); `apps/sync/mfa.mjs` — RFC 6238 и резервные коды; `apps/sync/pg/mfa.mjs` —
   запечатанный KEK секрет, одноразовый шаг, одноразовые резервные коды, таблица вызовов
   входа;
   `pnpm mfa:reset --as` завершает сессии и пишет `mfa.reset`.*
2. Подключение и резервные коды; второй шаг входа. *Сделано: `/account/mfa` (начало,
   подтверждение, новые резервные коды, отключение), `POST /auth/login` → `202 mfaRequired`,
   `POST /auth/login/mfa`, экран кода в форме входа, экран «Безопасность» в меню аккаунта.*
3. `mfa_at`, step-up, проверки на маршрутах `/operator/*`; правка `spec/operator.md` правило 6.
   *Сделано: 12 часов на чтение и 15 минут на изменение, `403 MFA_REQUIRED` с вызовом,
   `/operator/session/confirm` по коду, окно step-up в консоли.*
4. Письма, метрики, очистка неподтверждённых записей и просроченных вызовов.

## 11. Приёмка

- [ ] `pnpm verify` зелёный, с наборами базы.
- [ ] Проверка кода проходит векторы RFC 6238 (SHA-1, секрет `12345678901234567890`): T=59 →
      `287082`, T=1111111109 → `081804`, T=1234567890 → `005924`.
- [ ] Код из Яндекс Ключа и Google Authenticator принимается после подключения по QR и по
      ручному ключу; `issuer` — «Ремука (РФ)» на `app.remuka.ru` и «Remuka (EU)» на
      `app.remuka.com`.
- [ ] Тот же код второй раз отклоняется; код соседнего шага (±30 с) принимается; код через 2
      шага — нет.
- [ ] Оператор без TOTP на `/operator` попадает на подключение; API `/operator/*` отвечает
      `403 MFA_REQUIRED`.
- [ ] Вход: верный пароль без кода сессии не даёт; 5 неверных кодов сбрасывают вызов; 10 за
      час закрывают вход кодом на час и шлют письмо.
- [ ] Резервный код работает один раз; письмо с остатком приходит.
- [ ] Возврат в консоли через 20 минут после ввода кода требует код снова; чтение Пульса —
      нет.
- [ ] `pnpm mfa:reset` завершает все сессии и шлёт письмо; следующий вход в консоль требует
      подключения.
- [ ] Секрет в базе не читается без KEK; ни один ответ API после подключения не содержит
      секрета или `otpauth://`.
- [ ] По ответу `/auth/login` на неверный пароль нельзя понять, включён ли у аккаунта TOTP.
