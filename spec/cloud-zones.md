## 0. Зачем

Проверка 22 ноября (`node scripts/accept-rebrand.mjs`: 8 pass, 18 fail) показала, что
серверы расходятся с решениями:

- обе установки работают на **0.4.1, схема 20**; в репозитории — 0.8.0, схема 27;
- `app.remuka.com` и `app.remuka.ru` отвечают **308** на апекс, а приложение живёт на апексе;
- `remo.letii.ru` отвечает **308** на всё, включая `/api` и `/mcp`, — токены интеграций и MCP
  со старым адресом сейчас не работают;
- у `www.*` и `api.*` нет сертификатов;
- неизвестно, своя ли база у сервера РФ или это копия базы ЕС.

**В объёме:**

1. Целевая карта адресов обеих установок (§2).
2. Шаблоны nginx в репозитории и конфигурация на серверах (§4).
3. DNS и TLS (§3).
4. Окружение каждой установки (§5).
5. Проверка, что установка РФ независима и чиста (§6).
6. Выкладка 0.4.1 → 0.8.0 с репетицией и планом отката (§7).
7. Порядок работ по дням (§8) и приёмка (§9).

**Вне объёма:** лендинг, статус-страница и поддержка (Chatwoot) — только резерв адресов;
перенос сервера РФ на постоянный хостинг (будет отдельной процедурой по §7).

## 1. Правила, которые нельзя нарушить

1. **Установки не знают друг о друге.** Нет прокси, переадресаций и общих баз между ЕС и РФ.
   Единственная связь — ссылки между сайтами для человека.
2. **Постоянные переадресации (301, 308) — только там, где адрес меняется навсегда:**
   `www` → апекс, старый хост → новый. Апекс → приложение, пока нет лендинга, — только **302**.
   Браузер запоминает 301 и 308, и отменить их можно лишь у каждого человека отдельно.
3. **API, MCP и WebSocket на старом хосте проксируются, а не переадресуются**
   (`spec/rebrand.md` §6).
4. **У каждого имени в DNS — действующий сертификат, или записи нет.**
5. **Бэкап перед любой миграцией схемы** — скачанный к вам, а не только на том же сервере.
6. **Одна установка — одна команда выкладки**, с явным `REMO_DEPLOY_ENV_FILE`.
7. **Секреты не попадают в git и в это ТЗ.** IP-адреса серверов публичны (они в DNS) и могут быть
   в документации эксплуатации.

## 2. Целевая карта

Код ответа — для `GET /` и любого пути, если не сказано иное.

| Адрес | Установка | Ответ | Что за ним |
|---|---|---|---|
| `remuka.com` | ЕС | **302** → `https://app.remuka.com$request_uri` | Временная, пока нет лендинга; путь сохраняется |
| `www.remuka.com` | ЕС | 301 → `https://remuka.com$request_uri` | |
| `app.remuka.com` | ЕС | 200 | Приложение, `/api`, `/sync`, `/mcp`, `/help` |
| `docs.remuka.com` | ЕС | `/` → 302 `/guide/`; `/guide/*` → 200 | Гайд, `llms.txt` |
| `remo.letii.ru` | ЕС | страницы 301 → `app.remuka.com`; `/api`, `/mcp`, `/sync` — прокси | Блок «старый хост» из `deploy/nginx-remo.conf` |
| `docs.remo.letii.ru` | ЕС | 301 → `https://docs.remuka.com$request_uri` | |
| `remuka.ru` | РФ | **302** → `https://app.remuka.ru$request_uri` | Временная, пока нет лендинга |
| `www.remuka.ru` | РФ | 301 → `https://remuka.ru$request_uri` | |
| `app.remuka.ru` | РФ | 200 | Заглушка «Регион Россия готовится» до появления установки РФ (`spec/rebrand-fixes.md` §2); приложение — после решения §5.3 |
| `docs.remuka.ru` | РФ | как `docs.remuka.com` | `<link rel="canonical">` на `docs.remuka.com` |
| `api.remuka.com`, `api.remuka.ru` | — | **нет DNS-записей** | Резерв |
| `status.*`, `support.*` | — | нет записей до своих ТЗ | Резерв |

**Почему апекс отдаёт 302 с путём.** Сейчас приложение живёт на апексе, и ссылки на комнаты
вида `remuka.com/r/…` уже могли разойтись. 302 с `$request_uri` доведёт их до комнаты. Когда
появится лендинг, апекс начнёт отдавать сайт. Пути приложения (`/r/`, `/help/`, `/invite/` и
другие из роутера `apps/web`) тогда по-прежнему отдают 302 на `app.*`.

## 3. DNS и TLS

### 3.1 DNS

| Имя | Тип | Значение |
|---|---|---|
| `remuka.com`, `www`, `app`, `docs` | A | 87.106.94.6 |
| `remuka.ru`, `www`, `app`, `docs` | A | 185.171.83.153 |
| `remo.letii.ru`, `docs.remo.letii.ru` | A | 87.106.94.6 (сервер ЕС, без изменений) |
| `api.remuka.com`, `api.remuka.ru` | — | **удалить** |
| `remuka.com`, `remuka.ru` | CAA | `0 issue "letsencrypt.org"` |
| `mail.remuka.com` | TXT, CNAME, MX | по инструкции Resend: SPF, DKIM, return-path |
| `_dmarc.mail.remuka.com` | TXT | `v=DMARC1; p=quarantine; rua=mailto:dmarc@remuka.com` |
| `mail.remuka.ru` | — | после решения о почтовом провайдере РФ (§5.3) |
| MX апексов | MX | провайдер ящиков людей (`hello@`, `support@`, `privacy@`, `abuse@`, `security@`, `billing@`) — выбор владельца |

- AAAA-записи — только если на сервере настроен IPv6 и nginx слушает `[::]:443`. Иначе не
  заводить: половина клиентов будет ходить на неработающий адрес.
- За сутки до переключения записей (переезд сервера РФ, §8) — TTL 300.

### 3.2 TLS

- Сертификаты Let's Encrypt через certbot, по одному на имя или общий SAN на установку.
  - ЕС: `remuka.com`, `www.remuka.com`, `app.remuka.com`, `docs.remuka.com`, `remo.letii.ru`,
    `docs.remo.letii.ru`.
  - РФ: `remuka.ru`, `www.remuka.ru`, `app.remuka.ru`, `docs.remuka.ru`.
- Сертификат старого хоста продлевается минимум 12 месяцев.
- `certbot renew --dry-run` проходит на обоих серверах; таймер продления включён.
- **HSTS.** Апекс уже отдаёт `max-age=31536000`. Не добавлять `includeSubDomains` и `preload`,
  пока у каждого поддомена нет сертификата: иначе браузер закроет доступ ко всем
  поддоменам без сертификата на год.

## 4. nginx

### 4.1 Что меняется в репозитории

Шаблоны лежат в `deploy/`, на сервере в них подставляются имена. Секретов в них нет.

| Файл | Что внутри | Действие |
|---|---|---|
| `deploy/nginx-remo.conf` | Приложение (`server_name` подставляется) + блок «старый хост» | Без изменений; блок старого хоста используется только на сервере ЕС |
| `deploy/nginx-site.conf` | **Новый.** Апекс: 302 на приложение с путём; `www`: 301 на апекс; блоки 80 → 443 | Создать, переменные `SITE_HOST`, `APP_HOST` в комментарии сверху |
| `deploy/nginx-docs.conf` | **Новый.** Хост гайда: `/` → 302 `/guide/`, `/guide/` → `/srv/remo/docs-site/`, `nginx-security-headers-docs.conf` | Создать по образцу `location /guide/` из `nginx-remo.conf` |
| `docs/operations/cloud.md` | **Новый.** Эта карта (§2), DNS (§3.1), какие шаблоны на каком сервере, команды выкладки обеих установок | Создать; без секретов |

- Блок `location /guide/` в `nginx-remo.conf` остаётся: self-host без отдельного хоста гайда
  продолжает работать.
- `brand:check` уже разрешает `letii.ru` только в `deploy/nginx-remo.conf`. Новые шаблоны
  `letii.ru` не содержат.
- Сборка гайда ставит `<link rel="canonical" href="https://docs.remuka.com/…">` на каждой
  странице (`scripts/guide-build.mjs`, канонический адрес из `BRAND.domains.docs`). На обоих
  хостах гайда отдаются одни и те же файлы.

### 4.2 На серверах

Перед правкой — снимок текущей конфигурации:
`sudo tar czf ~/nginx-before-$(date +%F).tgz /etc/nginx`. Сначала найти и удалить все текущие
правила `return 308`.

**Сервер ЕС:**

1. `app.remuka.com` — из `nginx-remo.conf` (`server_name app.remuka.com`).
2. `remuka.com` и `www.remuka.com` — из `nginx-site.conf` (`SITE_HOST=remuka.com`,
   `APP_HOST=app.remuka.com`).
3. `docs.remuka.com` — из `nginx-docs.conf`.
4. `remo.letii.ru` и `docs.remo.letii.ru` — блок «старый хост» из `nginx-remo.conf`.

**Сервер РФ:**

1. `app.remuka.ru` — из `nginx-remo.conf`.
2. `remuka.ru` и `www.remuka.ru` — из `nginx-site.conf` (`SITE_HOST=remuka.ru`,
   `APP_HOST=app.remuka.ru`).
3. `docs.remuka.ru` — из `nginx-docs.conf`.
4. Блока старого хоста нет.

На каждом: `sudo nginx -t && sudo systemctl reload nginx`.

**Кэш постоянных переадресаций.** Тот, кто уже открывал `app.remuka.com` или `app.remuka.ru`,
получил от браузера запомненную 308 на апекс. После изменений апекс отдаёт 302 обратно — у
таких людей получится цикл. Лечится очисткой данных сайта в браузере. Людей таких немного —
адреса появились на днях. Если пожалуется кто-то из команды — это причина.

### 5.3 Почта установки РФ

Решение владельца с юристом. Resend находится в США, это трансграничная передача (раздел 3
юридических шаблонов). Варианты:

- российский SMTP-провайдер через драйвер `smtp` (`spec/mail.md`);
- Resend с доменом `mail.remuka.ru` и уведомлением Роскомнадзора о трансграничной передаче.

Пока решения нет, установка РФ не открывается для регистрации: без почты не работают
подтверждение адреса и сброс пароля.

## 6. Установка РФ: независимость и чистота

Сейчас обе установки отвечают одним коммитом `3565ff5`. Нужно проверить, что у РФ своя база
и в ней нет копии данных ЕС.

1. На сервере РФ: `docker ps` и `grep -E 'DB_HOST|DATABASE_URL' /srv/remo/shared/production.env`.
   База должна быть локальной (контейнер или PostgreSQL на этом же сервере), не адресом
   сервера ЕС.
2. Число аккаунтов и комнат в обеих базах:
   `psql "$DATABASE_URL" -c "select count(*) from accounts"` (точное имя таблицы — в
   `apps/sync/schema.sql`).
3. Если в базе РФ есть аккаунты, совпадающие с ЕС (сервер создавался копированием):
   - снять бэкап базы РФ к себе;
   - пересоздать пустую базу: `pnpm db:rls:setup`, затем миграции выкладкой;
   - записать в журнал эксплуатации, что копия удалена.

   Данные граждан РФ в установке ЕС остаются вопросом к юристу (`spec/rebrand.md` §5.1).
4. `REMO_KEK` у установки РФ — свой, не скопированный с ЕС. Если скопирован, а база пустая —
   сгенерировать новый до первой регистрации.

## 7. Выкладка 0.4.1 → 0.8.0

Между версиями четыре релиза и схема 20 → 27 (почта, изображения, биллинг, rich text,
ребрендинг).

1. **Репетиция.** Последний бэкап ЕС восстановить на тестовой машине (`pnpm db:restore` или
   отдельный VPS), выкатить на неё 0.8.0 тем же `deploy/release.sh` с третьим файлом
   выкладки. Ожидается: миграция проходит, `/api/health` → `0.8.0`, `schema 27`, старые
   комнаты открываются, бэкап 0.4.1 импортируется. Время миграции записать — это окно
   простоя на проде.
2. **Бэкап прода** обеих установок, скачать к себе: `pnpm db:backup` на сервере или
   `remo-backup.service`, затем `scp`. Проверить, что архив открывается.
3. **Выкладка ЕС:**
   `REMO_DEPLOY_ENV_FILE=.config/remo/com.env.local bash deploy/release.sh`.
   Скрипт сам проверяет дамп, миграцию, коммит и схему.
4. **Выкладка РФ** — отдельной командой, после §6:
   `REMO_DEPLOY_ENV_FILE=.config/remo/ru.env.local bash deploy/release.sh`.
5. **Откат.** Ревизии, образы и проверенные дампы остаются на сервере (`docs/self-hosting.md`,
   «Releases»). Порядок отката записать в `docs/operations/cloud.md` до выкладки: какая
   команда возвращает предыдущую ревизию, как восстановить дамп.
