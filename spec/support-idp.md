# Вход операторов панели агента: Authelia на хосте поддержки

ТЗ к [ADR-291](../ADR.md#adr-291-support-panel-staff-sign-in-through-authelia-on-the-support-host).
Дата: 2026-11-24. Статус: **решение владельца принято; реализация не заявлена.**
Связано: [support-agent.md](support-agent.md) §2, §11, §13, §16; [support-agent-ui.md](support-agent-ui.md)
(S-UI1, артборд `Support-Access`); [support.md](support.md) §3.1; `deploy/support/README.md`.

## 1. Что решаем и чего не делаем

Панели `/agent/` нужен провайдер входа (OIDC) с группами ролей и вторым шагом. Его не было:
`support-agent.md` §2 называл это отдельной инфраструктурной задачей. Решение владельца
24.11: **свой лёгкий провайдер Authelia на каждом хосте поддержки**, пользователи и группы
в файле, второй шаг — TOTP или ключ (WebAuthn/passkey).

Не делаем:
- единый вход в Chatwoot: учётные записи сотрудников Chatwoot остаются отдельными (§3.1 `support.md`);
- вход клиентов Ремуки или сотрудников в продукт через Authelia — только панель агента;
- облачного провайдера и общего IdP на все зоны: учётные записи сотрудников RU не уходят в ЕС
  и наоборот;
- самостоятельной регистрации и сброса пароля по почте.

## 2. Где стоит

| Что | Значение |
|---|---|
| Хост | тот же `support.<домен>`, что и Chatwoot и `remo-support-agent` (OPS-02: без нового поддомена) |
| Адрес провайдера (issuer) | `https://support.<домен>/auth` — подпуть, не поддомен |
| Контейнер | `authelia/authelia` по **digest образа**, версия записана в README и матрице совместимости |
| Сеть | внутренняя сеть compose; наружу только через ingress хоста поддержки (`location /auth/`) |
| Хранилище | SQLite в томе `authelia-data` (устройства второго шага, согласия); шифрование ключом `storage.encryption_key` |
| Пользователи | `users.yml` в томе конфигурации, mode 600, вне git и образа; `watch: true` — правка без перезапуска |
| Почта | уведомления Authelia (коды подтверждения при регистрации устройства) — через SMTP установки, отдельная учётная запись |
| Память | цель — десятки МБ; замерить на stage вместе с OPS-03 и записать в протокол, не считать заранее |

Одна установка Authelia обслуживает все установки агента на этом хосте (например, stage-ru и
stage-eu на общем стенде). На проде RU и EU — разные хосты и разные Authelia; списки
сотрудников не синхронизируются автоматически.

## 3. Группы и роли

Группы называются по установке, чтобы роль в одной установке не давала доступа к другой
(§2 ТЗ, A31):

```
support-<installation>-admin      → администратор поддержки
support-<installation>-operator   → оператор
support-<installation>-analyst    → аналитик
<installation> = stage-ru | stage-eu | prod-ru | prod-eu
```

- Соответствие «группа → роль» задаётся при установке агента (bootstrap env, OPS-01) и не
  редактируется из панели или промпта.
- Пользователь без группы своей установки входит в Authelia, но панель отвечает
  «Нет доступа к этой установке» (`Support-Access`, `forbidden`, 403 `no_role`).
- Несколько групп одной установки — берётся старшая роль: admin > operator > analyst.
- Группы читаются из ID token (claim `groups`, scope `groups`) при каждом входе; сессия панели
  хранит роль и время входа.

## 4. Настройки Authelia (обязательные)

Конфигурация — шаблон в репозитории без секретов; секреты — файлами (`*_FILE`) из
`/srv/<support>/authelia/secrets/`, mode 600.

| Раздел | Значение |
|---|---|
| `server.address` | `tcp://:9091/auth` |
| `authentication_backend.file` | `users.yml`, `watch: true`, хеш argon2id; `password_reset.disable: true` |
| `password_policy` | `zxcvbn`, минимальная оценка 3 |
| `totp` | issuer `Ремука · поддержка <installation>`, период 30 с, 6 цифр |
| `webauthn` | включён; `user_verification: preferred` |
| `access_control` | `default_policy: deny`; домен хоста поддержки — `two_factor` |
| `regulation` | 5 попыток за 2 мин → блок 10 мин |
| `session` | cookie на `support.<домен>`, `Secure`, `SameSite=lax`; бездействие 30 мин, срок 8 ч |
| `identity_providers.oidc` | ключ подписи RS256 (jwks), `hmac_secret`, срок кода 1 мин, ID token 1 ч; `enforce_pkce: always` |
| Клиент `remo-support-agent` | confidential, `client_secret` хешем; `redirect_uris: https://support.<домен>/agent/auth/callback`; scopes `openid profile email groups`; `authorization_policy: two_factor`; `consent_mode: implicit`; `token_endpoint_auth_method: client_secret_basic` |
| `notifier.smtp` | SMTP установки, отправитель `support-auth@<домен>` |
| `log` | `info`, JSON, без паролей и кодов |

Второй шаг обязателен **для всех ролей**, не только для администратора: сотрудников мало, а
панель видит обращения клиентов. Это строже требования §2 ТЗ и его не нарушает.

## 5. Панель агента как клиент OIDC

Панель знает только стандарт OIDC, ничего специфичного для Authelia — замена провайдера
(Keycloak, Zitadel) не меняет код, только bootstrap env.

- Authorization Code + PKCE (S256), `state` и `nonce` на каждый вход; проверка `iss`, `aud`,
  подписи по JWKS провайдера, `exp`, `nonce`; короткоживущие коды и токены в журнал не пишутся.
- Серверная сессия `httpOnly`, `Secure`, `SameSite=lax`, CSRF на мутациях; бездействие 30 мин,
  абсолютный срок 8 ч, затем вход заново (`Support-Access`, `expired`; черновик настроек не теряется).
- Выход из панели закрывает свою сессию и ведёт на выход Authelia
  (RP-Initiated Logout, если поддерживается закреплённой версией; иначе — ссылка `/auth/logout`).
- Аудит: вход, отказ по роли, выход, отзыв сессии — actor, установка, время, IP-подсеть, без токенов.

## 6. Жизненный цикл сотрудника (runbook)

Всё делает администратор хоста поддержки по SSH; панель этим не управляет.

| Действие | Как | Проверка |
|---|---|---|
| Добавить | `authelia crypto hash generate argon2` → запись в `users.yml` (email, группы) → передать временный пароль лично | вход, регистрация TOTP/ключа по коду из письма, роль в шапке панели |
| Изменить роль | правка групп в `users.yml` | действует со следующего входа; для немедленного — отзыв сессии |
| Отозвать | удалить пользователя из `users.yml` → `remo-support-agent sessions:revoke --user <email>` (команда агента, аудит) | следующий запрос панели — 401 и экран входа |
| Потеря устройства | удалить устройство: `authelia storage user totp delete` / `webauthn delete` → повторная регистрация | вход только после новой регистрации |
| Забыл пароль | администратор выдаёт новый хеш; сброса по почте нет | — |

Отзыв обязателен в тот же день, что и уход сотрудника; запись — в журнал операций хоста.

## 7. Бэкап, обновление, отказ

- В бэкап хоста: `users.yml`, том `authelia-data`, шаблон конфигурации. Секреты
  (`storage.encryption_key`, jwks, `hmac_secret`, client secret) — отдельно, как KEK агента (OPS-07).
  Без `storage.encryption_key` устройства второго шага не расшифровать — тогда все
  перерегистрируются.
- Обновление: новый digest → stage → сценарии §8 → прод. OIDC-провайдер Authelia — открытая
  бета: перед обновлением читать release notes на изменения OIDC, версию не обновлять «вслепую».
- Отказ Authelia: панель недоступна (вход невозможен), **агент, виджет и Chatwoot работают** —
  они от Authelia не зависят. Пауза агента в этом случае — через CLI агента (аудит).

## 8. Задание S-IDP1

Этап S1 (инфраструктура), до S-UI1. Пока репозитория агента нет, файлы кладутся в
`deploy/support/authelia/` этого репозитория рядом с конфигурацией виджета.

**Результат:**
1. `deploy/support/authelia/configuration.yml.tmpl` (§4, без секретов), `users.yml.example`
   (два вымышленных пользователя), `compose.authelia.yml` (сервис, тома, healthcheck, digest).
2. `deploy/support/authelia/gen-secrets.sh` — создаёт секреты в `/srv/<support>/authelia/secrets/`
   с mode 600, не перезаписывает существующие.
3. Блок `location /auth/` в `deploy/support/nginx.conf` и в stage `support.conf`: прокси на
   `authelia:9091`, заголовки `X-Forwarded-*`, без кэша; на stage — за паролем стенда.
4. `docs/operations/support-idp.md` — установка, runbook §6, бэкап и обновление §7 (RU).
5. Строка в матрице совместимости: версия Authelia, digest, проверенные функции (PKCE,
   claim `groups`, WebAuthn, RP-Initiated Logout — да/нет).

**Проверки (протокол прикладывается):**

| # | Действие | Ожидаемо |
|---|---|---|
| I1 | `/.well-known/openid-configuration` по `https://support.<домен>/auth` | issuer совпадает, PKCE S256 в списке |
| I2 | Вход тестовым пользователем без второго шага | Authelia требует TOTP/ключ, код не выдан |
| I3 | Тестовый клиент: код без `code_verifier`, чужой `redirect_uri` | отказ |
| I4 | Пользователь с группой `support-stage-eu-admin` входит в stage-ru | ID token выдан, панель отвечает 403 `no_role` (проверяется в S-UI1) |
| I5 | 6 неверных паролей подряд | блок по `regulation`, событие в журнале |
| I6 | Удаление из `users.yml` + `sessions:revoke` | следующий запрос панели — экран входа |
| I7 | Остановить Authelia | Chatwoot, виджет и ответы агента работают |
| I8 | Восстановление из бэкапа в чистый том | вход с прежним TOTP |
| I9 | Замер RSS под 5 входами подряд | цифра в протоколе OPS-03 |

Связь с приёмкой агента: A27 (роли, неверный OIDC/CSRF) и A31 (изоляция установок)
выполняются уже против этого провайдера.
