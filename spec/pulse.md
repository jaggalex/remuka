# «Пульс»: продуктовые и бизнес-метрики и панель оператора

ТЗ к **ADR-258**, развивает ADR-082 и `spec/metrics.md`. Статус: предложено, 2026-11-23.
Прежде чем менять код, прочитайте `AGENTS.md`, ADR-082, `spec/metrics.md`, `spec/billing.md`
(ADR-247), `spec/cookies.md` (ADR-255), `spec/rebrand.md` §5.1 (две установки).

## 0. Зачем и что в объёме

`spec/metrics.md` уже задаёт основу: типизированные события в `packages/metrics`, отдельная
база `remo_metrics`, никаких имён, e-mail и IP, активация, TTFV, когорты, качество ИИ. Не
хватает пяти вещей:

1. **Денег.** В `metrics.md` написано, что конверсия, GRR и NRR не считаются, потому что
   биллинга нет. Биллинг появился (ADR-247), поэтому теперь их можно считать.
2. **Источников.** Неизвестно, откуда приходят новые организации. Трекеров на сайте нет, и
   по ADR-255 их нельзя ставить без согласия.
3. **Совместной работы** — главной ценности продукта. Сейчас она видна только косвенно.
4. **Двух установок.** У ЕС и РФ свои базы метрик; общей картины нет.
5. **Панели.** Отчёты описаны как SQL-вьюхи, но смотреть их негде.

**В объёме:** дерево метрик (§1), недостающие события (§2), источники без cookie (§3),
ежедневные агрегаты (§4), сведение двух зон (§5), панель «Пульс» в приложении (§6),
еженедельная сводка и пороги (§7).

**Вне объёма:** внешние BI-системы (вьюхи §4 позволяют подключить их позже), сторонняя
веб-аналитика, A/B-тесты.

## 1. Дерево метрик

### 1.1 Главная метрика

**Совместно работающие команды за неделю (WACT, Weekly Active Collaborative Teams)** —
организации, в которых **за календарную неделю хотя бы двое людей** сделали value event
(`spec/metrics.md`: сохранение с изменениями, объект, связь, применённая задача агента).

Почему эта метрика:
- Ремука продаёт совместную работу: одиночное использование — это заметки, а не продукт;
- метрика растёт, только когда растут привлечение, активация, приглашения и удержание;
- она одинаково понятна для команды, класса и семьи.

### 1.2 Метрики, из которых она складывается

| Группа | Метрика | Определение |
|---|---|---|
| Привлечение | Новые организации | `org.created`, по источнику (§3) |
| Привлечение | Конверсия сайта | регистрации / уникальные визиты сайта за день, по источнику |
| Активация | Activation 7d, TTFV | как в `spec/metrics.md` |
| Распространение | Invite rate 7d | доля новых организаций, отправивших ≥1 приглашение за 7 дней |
| Распространение | Invite acceptance | принятые / отправленные приглашения |
| Распространение | Collaboration rate | доля активных организаций, где за неделю ≥2 человека |
| Вовлечённость | DAU, WAU, MAU, stickiness | как в `metrics.md`; stickiness = DAU/MAU |
| Вовлечённость | Совместные сессии | комнаты, где ≥2 человека правили одновременно (окно 10 минут) |
| Вовлечённость | Использование функций | доля WAU-организаций, использовавших функцию за неделю: канбан, таймер, голосование, презентация, агент, изображения, форматирование текста, шаблоны |
| Удержание | Retention W1, W4, W12 | когорты организаций по неделе создания (`metrics.md`) |

### 1.3 Деньги

Источник истины — таблицы биллинга, а не события (одна работа — один механизм).

| Метрика | Определение |
|---|---|
| MRR | сумма активных подписок, приведённых к месяцу (годовая / 12), **отдельно по валютам**; итог в USD — по курсу, который оператор вводит раз в месяц |
| Платящие организации | организации с активной платной подпиской |
| ARPA | MRR / платящие организации |
| Free → paid | доля организаций, перешедших на платный тариф в течение 30 и 90 дней от создания |
| Trial → paid | доля пробных периодов Team/Business, закончившихся оплатой |
| Logo churn | организации, у которых платная подписка закончилась за месяц / платящие на начало месяца |
| GRR, NRR | по MRR когорты платящих на начало месяца: без расширений / с расширениями |
| Восстановление платежей | доля неуспешных списаний, оплаченных в льготный срок |
| Упор в лимит | `limit.hit` по лимиту и тарифу — сигнал к переходу на платный тариф |
| До безубыточности | платящие команды / порог из модели цен (сейчас 43); порог — настройка оператора |

### 1.4 Здоровье (ограничители)

Рост не засчитывается, если ухудшилось здоровье. Эти цифры уже есть в метриках Prometheus
(`remo_*`); панель показывает их сводку.

- Доля ошибок сохранения: `remo_store_write_errors_total` / `remo_store_writes_total`.
- Отказы WebSocket и закрытия по квоте.
- Недоставленные письма (`remo_mail_dead_total`).
- Отказы шлюза ИИ (`remo_ai_gateway_unavailable_total`).
- Обращения в поддержку за неделю и доля решённых агентом поддержки — из Chatwoot, когда он
  включён (ADR-250).

## 2. Недостающие события

Добавляются в `METRIC_CATALOG` (`packages/metrics`) по правилам `metrics.md`: только UUID и
скалярные свойства.

| Событие | Где | Свойства |
|---|---|---|
| `signup.completed` | `POST /auth/register` | `source`, `medium`, `campaign`, `zone`, `via` (`direct`, `invitation`, `link`) |
| `invitation.accepted` | `/invitations/accept` | `role`, `ageHours` |
| `collab.session` | sync, при закрытии окна совместной правки | `participants`, `durationMin` — только число, без id участников |
| `template.used` | создание комнаты из шаблона | `templateId` |
| `feature.used` | первый раз за день на организацию | `feature` из закрытого списка §1.2 |
| `chrome.used` | запуск команды реестра хрома (ADR-294) | `control` из закрытого списка `CHROME_CONTROLS`; первое нажатие за день на организацию |
| `limit.hit` | проверка `entitlementsFor` отказала | `limit`, `plan` |
| `upgrade.viewed`, `checkout.started` | панель тарифов, переход к оплате | `plan`, `interval`, `currency` |
| `pulse.viewed` | открытие панели оператора | — (чтобы видеть, что панелью пользуются) |

`billing.*` из `metrics.md` больше не нужны: деньги считаются по таблицам биллинга (§1.3).

## 3. Источники без cookie

ADR-255 не позволяет ставить аналитику на сайт без согласия, и это правильно. Источники
считаются без идентификаторов в браузере:

1. **Метки в ссылках.** Все кнопки регистрации на сайтах, в рассылках и в постах несут
   `?utm_source=…&utm_medium=…&utm_campaign=…`. Приложение передаёт их в
   `POST /auth/register` как часть запроса. Сервер пишет их в `signup.completed` и в
   `orgs.source` (новая колонка, без персональных данных). Учитывается только первое
   касание; связи между сайтами нет.
2. **Сайт, с которого пришёл человек** (HTTP-заголовок `Referer`, который браузер отправляет
   сам; это не реферальная программа). Если меток нет, в `source` пишется только домен этого
   сайта, без пути (`habr.com`, `t.me`); если заголовка нет — `direct`.
3. **Визиты сайтов.** Скрипт `scripts/site-stats.mjs` раз в сутки читает журналы nginx сайтов
   и гайда и пишет в `site_daily`: дата, хост, путь, домен реферера, `utm_*`, число запросов и
   число уникальных пар «IP + User-Agent» **за этот день**. Сами IP и User-Agent не
   сохраняются; журналы nginx хранятся 7 дней (`logrotate`). Боты отсекаются по списку
   User-Agent.
   - *Юристу:* подтвердить, что подсчёт уникальных за день без хранения IP не требует согласия
     в обеих зонах.

## 4. Агрегаты

Один писатель — ночной агрегатор. Панель, сводка, CSV и BI только читают. Формула каждой
метрики живёт в одном месте (`apps/sync/pulse/*.mjs`), таблица — в базе метрик, не в
продуктовой.

### 4.1 Хранилище и DDL

`metrics_daily` лежит в базе `remo_metrics` (`REMO_METRICS_DATABASE_URL`). DDL — в
`METRICS_SCHEMA` (`apps/sync/metrics-store.mjs`); его применяют `pnpm db:metrics` и старт
сервиса (`MetricsStore.connect`). Продуктовый `schema.sql` и `SCHEMA_VERSION` не меняются:
база метрик отдельная (ADR-082) и своей версии схемы не имеет, а `create table if not exists`
идемпотентен.

```sql
create table if not exists metrics_daily (
  day date not null,                    -- UTC-дата; у недели и месяца — последний день периода
  zone text not null check (zone in ('eu', 'ru', 'none')),
  metric text not null,                 -- имя метрики §1.2–1.3, например orgs.created
  dims jsonb not null default '{}'::jsonb,   -- закрытый список ключей, см. ниже
  value bigint,                         -- счётчик, минорные единицы валюты или микро-USD
  status text not null default 'ok' check (status in ('ok', 'suppressed', 'unavailable')),
  basis text not null default 'derived' check (basis in ('derived', 'snapshot', 'rebuilt')),
  provenance text not null default 'local' check (provenance in ('local', 'peer')),
  computed_at timestamptz not null default now(),
  primary key (day, zone, metric, dims),
  constraint metrics_daily_value_check
    check ((status = 'ok') = (value is not null) and (value is null or value >= 0)),
  constraint metrics_daily_dims_check check (
    dims - 'period' - 'plan' - 'currency' - 'source' - 'feature' - 'template' - 'skill'
         - 'cohort' - 'offset' - 'control' = '{}'::jsonb
  ),
  constraint metrics_daily_no_email_check check (strpos(dims::text, '@') = 0)
);
create index if not exists metrics_daily_metric_idx on metrics_daily (metric, zone, day);
create index if not exists metrics_daily_peer_idx
  on metrics_daily (zone, day) where provenance = 'peer';
```

Колонки:

- **`value` — целое.** Деньги — в минорных единицах валюты (`dims.currency`), стоимость ИИ —
  в микро-USD, счётчики — штуки. Дробей и процентов в таблице нет: доля (активация, удержание,
  GRR/NRR) считается на чтении из двух строк — числителя и знаменателя. Процент, положенный в
  базу, теряет базу и не складывается.
- **`status`.** `ok` — значение есть, в том числе честный `0`; `unavailable` — посчитать
  нельзя (пустая когорта, нет источника), `value` пуст, панель показывает «—» с причиной;
  `suppressed` — значение скрыто при выгрузке (§5.1), `value` пуст. Проверка в схеме не даёт
  записать `0` вместо «нельзя посчитать».
- **`basis`.** `derived` — выводится из событий и уже записанных строк, пересчитывается
  свободно; `snapshot` — состояние биллинга на момент первой записи дня; `rebuilt` — то же
  состояние, снятое позже (догон, ручной пересчёт), панель помечает такие точки как оценку.
- **`provenance`.** `local` — посчитано здесь; `peer` — получено от второй зоны (§5.3).
  Локальный пересчёт никогда не трогает `peer`, а выгрузка никогда не берёт `peer`.
- **`dims`** — только закрытые ключи: `period` (`week` | `month`), `plan`, `currency`
  (ISO 4217), `source`, `feature`, `template`, `skill`, `cohort` (понедельник недели когорты,
  `YYYY-MM-DD`), `offset` (неделя удержания 0…12), `control` (id реестра команд, ADR-294).
  Пустой объект — метрика без разрезов; `null`
  не пишется, отсутствующий разрез — отсутствующий ключ. Значения нормализуются при записи:
  нижний регистр, `[a-z0-9._-]`, не длиннее 40 символов, неизвестное — `other`. Идентификатора
  организации, человека, комнаты или сессии здесь нет и быть не может: лишний ключ отвергает
  `metrics_daily_dims_check`, символ `@` — `metrics_daily_no_email_check`.
- Строка на `(day, zone, metric, dims)` одна: первичный ключ и есть идемпотентность (§4.4).

Неделя — понедельник–воскресенье UTC, недельная строка пишется на воскресенье; месячная — на
последнее число. Дневная строка ключа `period` не имеет. Недельная и месячная строка живут на
последнем дне периода, поэтому рядом с дневной строкой того же дня это разные ключи.

### 4.2 Кто и когда пишет

Единственный писатель — агрегатор `apps/sync/pulse/aggregate.mjs`, запускаемый таймером в
`server.mjs` по образцу `mail-drain.mjs`: каждый день в **03:10 UTC** он пересчитывает
`D−1 … D−3`. Три дня, потому что событие пишется best-effort (`metrics-store.record` глотает
сбой базы) и поздняя запись может прийти после полуночи; три ночи подряд закрывают почти все
поздние записи, а идемпотентность делает повтор безопасным.

Ни маршрут API, ни панель, ни экспорт в `metrics_daily` не пишут. Сборщик зоны (§5.3) пишет
только `provenance = 'peer'`, агрегатор — только `local`.

Незаконченный период не пишется: дня «сегодня», текущей недели и текущего месяца в таблице
нет. Панель показывает последний полный день или неделю и подписывает его датой; текущая
неделя не рисуется точкой, чтобы неполная неделя не выглядела падением.

Все запросы агрегатора идут с `set local time zone 'UTC'` в транзакции: `current_date` иначе
зависит от зоны сессии PostgreSQL, и «вчера» на сервере в Москве оказалось бы другим днём.
Часовой пояс хранения — UTC и только UTC; московское время — вопрос подписи на экране, не
границы дня.

### 4.3 Как считается

Каждая метрика §1.2–1.3 — функция `compute<Metric>(day)` в `apps/sync/pulse/`, читающая
`metrics_events`, таблицы биллинга (только чтение) и `site_daily`. Каталог
(`apps/sync/pulse/catalog.mjs`) перечисляет имя, единицу, допустимые разрезы и класс
(`derived` или `snapshot`); тест требует фикстуру с заранее посчитанным ответом для каждой
записи каталога.

- Дневные метрики пишутся на свой день.
- Недельные и месячные (WACT, DAU/WAU/MAU, удержание, GRR/NRR) считаются **из событий**, а не
  сложением дневных строк: уникальные люди и организации не аддитивны. Пишутся на последний
  день периода с `dims.period`; удержание — с `dims.cohort` и `dims.offset`.
- Деньги — снимок биллинга: `money.mrr` по `dims.currency` и `dims.plan`, `money.paying`.
  Снимок за день D снимается первым прогоном после конца D и больше не переписывается
  (`on conflict do nothing`): восстановить состояние подписок на прошлую дату из текущих таблиц
  нельзя, а перезапись задним числом сделала бы историю выдуманной. Пропущенный день догоняется
  позже и получает `basis = 'rebuilt'`. Исправление биллинга задним числом в историю MRR не
  попадает — история это снимки, а не реконструкция.
- Здоровье §1.4 в `metrics_daily` не пишется: это счётчики Prometheus, панель читает их как
  сейчас.
- Вьюхи `pulse_*` над `metrics_daily` — для внешнего BI; они ничего не пишут.

### 4.4 Пересчёт, идемпотентность, пропуск дня

Единица пересчёта — день. `recompute(from, to)`:

1. `to = min(to, вчера UTC)`; `from = max(from, сегодня − 730, первый день с событиями)`. Если
   `from > to` — делать нечего.
2. Затронутые дни — каждый день `[from, to]` плюс последний день каждого **закончившегося**
   периода (недели, месяца), в который попадает хотя бы один день диапазона. Поэтому позднее
   событие пересчитывает и свою неделю, и свой месяц, а незаконченный период не появляется.
3. Каждый затронутый день — одна транзакция под
   `pg_advisory_xact_lock(hashtext('pulse:' || day))`. Строки пишутся
   `insert … on conflict (day, zone, metric, dims) do update set value = excluded.value,
   status = excluded.status, basis = excluded.basis, computed_at = now()
   where metrics_daily.provenance = 'local'`; снимок денег вставляет `do nothing`. Затем в той
   же транзакции удаляются локальные строки этого дня, которых в новом наборе нет. Удаление —
   в пределах вида строки: дневные (`dims` без `period`), недельные, месячные. День `W_end`
   держит и удержание по когортам `W−k`, поэтому чистить его целиком нельзя.
4. Сбой дня откатывает только его: цикл идёт дальше. `pulse:recompute` завершается ненулевым
   кодом, таймер пишет ошибку в лог. Следующая ночь всё равно берёт `D−1 … D−3`.

Команды и запуск:

- `pnpm pulse:recompute --from 2026-11-01 --to 2026-11-23` — тот же код и тот же замок; отказ
  за пределами 730 дней и по будущим датам.
- Ночной прогон и догон при старте: `from = max(day) + 1` (или `вчера − 2`, если строк нет) до
  вчера. Догон идёт в фоне после `listen` и не задерживает приём запросов; каждый день — строка
  в логе.

Пропуск дня:

- До трёх ночей пропуск закрывается сам: окно `D−1 … D−3` пересчитывает те же дни.
- Больший (отпуск, авария) закрывает догон при старте, день за днём; в лог —
  `[pulse] catch-up N days`, в метрику — `remo_pulse_recompute_days_total{result}`.
- День, который так и не пересчитан, — **дыра, а не ноль**: строк нет, панель показывает «—»
  с причиной «день не пересчитан», сводка перечисляет пропущенные дни. День без событий — это
  настоящий ноль: строки с `value = 0` пишутся. Отличить простой установки от отсутствия
  использования база метрик не может и не утверждает.
- Свежесть — `max(day)` и `max(computed_at)`; `remo_pulse_last_success_timestamp_seconds` даёт
  алерт, если ночь не прошла.

### 4.5 Хранение

Окно — **24 месяца (730 дней)**: 26 недель панели, 12 недель удержания, месяц к месяцу по
GRR/NRR и год к году по MRR с запасом. Раз в неделю тот же агрегатор удаляет
`day < current_date − 730` — и локальные строки, и полученные. `pulse:recompute` старше окна
отказывает.

`metrics_events` хранится **400 дней** (ADR-263): этого хватает на исправления и запуск, а
глубже пересчёт всё равно невозможен без событий. Оба срока удаляет один недельный проход
агрегатора. Пересчёт возможен только за дни, где события ещё есть; агрегат старше потока
остаётся записью.

### 4.6 Чтение

После этого этапа панель, сводка и CSV читают продуктовые и событийные числа только из
`metrics_daily`; здоровье остаётся из Prometheus (§4.3). Живые запросы панели к
`metrics_events` и биллингу убираются: иначе плитка и её линия за 12 недель могут разойтись.
Ответ панели называет последний полный день и `computed_at`; отсутствующая строка — «—» с
причиной, а не `0`.

## 5. Две установки — одна картина

У ЕС и РФ свои базы, и персональные данные между ними не ходят (ADR-254 §5.1). Ходят только
агрегаты и в одну сторону: установка, у которой задан `REMO_PULSE_PEERS`, забирает чужие
строки; отдающая сторона только отвечает. Обмен есть только у установки с
`REMO_COMPLIANCE_ZONE` = `eu` или `ru`; при `none` ни маршрута экспорта, ни сборщика нет.

### 5.1 Что можно отдавать

Ровно строки `metrics_daily` своей зоны с `provenance = 'local'` — счётчики и суммы §1.2–1.3.
Метрик про оператора (`pulse.viewed`) в §1 нет, поэтому в выгрузку они не попадают. `status`
передаётся любой: `unavailable` и `suppressed` тоже, чтобы вторая установка показывала «—» и
«<5», а не пустоту.

Можно: новые организации, активацию (числитель и знаменатель), DAU/WAU/MAU, WACT, совместные
сессии, использование функций и шаблонов, удержание по когортам, дневные визиты сайта, MRR в
минорных единицах по валютам и тарифам, платящие организации, GRR/NRR, упор в лимиты.

Нельзя и не выгружается никогда:

- `metrics_events` — ни строки, ни выборки, ни агрегата «на лету»;
- `site_daily` — путь и реферер это след поведения, а не метрика;
- биллинг: счета, платежи, `payment_methods`, `provider_subscription_id`, e-mail плательщика;
- аудит и поддержка (Chatwoot) — это про оператора, а не про клиентов;
- любой `org_id`, `actor_id`, `board_id`, `session_id`, e-mail, IP, User-Agent.

Деньги едут только в своей валюте и минорных единицах. Курс и итог в USD каждая установка
считает своим курсом оператора (§1.3); курс между зонами не передаётся — иначе одна установка
молча меняла бы числа другой. Нет курса — «—».

**Малые числа.** Если в `dims` есть `source`, `template`, `feature`, `skill` или `control` и
`0 ≤ value < 5`, при выгрузке значение заменяется на `status = 'suppressed'` без `value`.
Подавление — свойство выгрузки, а не хранилища: у себя установка видит свои настоящие числа.
Список подавляемых разрезов — закрытая константа с тестом; новый разрез по внешнему признаку
добавляется в неё, а не в конфиг (ADR-263 расширил пару `source`/`template` до всех четырёх;
ADR-294 добавил `control`).

Объём одного ответа — не больше 366 дней и 8 МиБ; сборщик просит окнами по 30 дней.

### 5.2 Как передаётся

`GET /operator/pulse/export?from=YYYY-MM-DD&to=YYYY-MM-DD` (снаружи `/api/operator/...`: nginx
снимает `/api`, как у остальных маршрутов).

- **Только HTTPS и только с токеном:** `Authorization: Bearer <REMO_PULSE_TOKEN>`. Обе стороны
  сравнивают SHA-256 от токена через `timingSafeEqual`; неверный или отсутствующий токен —
  `404`, как у всей консоли. Без `REMO_PULSE_TOKEN` маршрута нет.
- Это машинный маршрут: сессии, cookie и CSRF здесь нет. Проверка токена стоит **до** сессионной
  проверки консоли — единственное исключение из правила «всё под `/operator` требует сессии».
- Клиент отказывается от не-HTTPS адреса, от адреса в приватной сети и не идёт по
  переадресациям (ADR-109); таймаут 30 с.
- Даты проверяются: `from ≤ to ≤ вчера UTC`, окно не больше 366 дней; иначе `400`, а не
  молчаливая обрезка.
- Тело — JSON, `Content-Type: application/json; charset=utf-8`, `Cache-Control: no-store`:

```json
{
  "version": 1,
  "zone": "ru",
  "generatedAt": "2026-11-23T03:00:00Z",
  "from": "2026-10-24",
  "to": "2026-11-22",
  "rows": [
    { "day": "2026-11-22", "metric": "orgs.created", "dims": { "source": "habr" },
      "value": 12, "status": "ok", "basis": "derived" },
    { "day": "2026-11-22", "metric": "orgs.created", "dims": { "source": "t.me" },
      "status": "suppressed", "basis": "derived" },
    { "day": "2026-11-22", "metric": "activation.reached", "dims": {},
      "status": "unavailable", "basis": "derived" },
    { "day": "2026-11-16", "metric": "collab.teams", "dims": { "period": "week" },
      "value": 7, "status": "ok", "basis": "derived" }
  ]
}
```

- Строки отсортированы (`day`, `metric`, `dims`), чтобы одинаковые данные давали одинаковое
  тело.
- Подпись — `X-Pulse-Signature: sha256=<hex>`, HMAC-SHA256 по **точным байтам** тела тем же
  токеном. Получатель проверяет подпись до разбора JSON; сжатие на этом маршруте выключено,
  иначе подпись не сойдётся. Подпись защищает байты в пути и от подмены прокси, но не от второй
  стороны: ключ у обеих сторон один.
- Отправитель пишет одну строку в лог (origin, `from`, `to`, число строк) и увеличивает
  `remo_pulse_export_rows_total`; тело, IP и User-Agent не сохраняются нигде. Маршрут ничего не
  пишет в базы.

### 5.3 Кто инициатор и что хранится у получателя

Инициатор — только установка ЕС: `REMO_PULSE_PEERS` (список origin через запятую; в облаке
один адрес `https://app.remuka.ru`). Установка РФ наружу не ходит: одна точка сбора, одни
часы, одно место для отладки, и с российского сервера нет исходящих соединений в ЕС. Пульс на
РФ-установке показывает свою зону и причину, почему второй нет (ADR-263).

Сборщик `apps/sync/pulse/peer-collect.mjs` — раз в час в `:20`:

- окно — с `max(day) − 2` по вчера; первый сбор — 200 дней (26 недель панели с запасом),
  окнами по 30 дней;
- один повтор с задержкой, затем `last_error` и следующий час; бесконечных повторов нет;
- зона запоминается при первом успешном сборе (`pulse_peers.zone`) и дальше обязана совпадать
  с `zone` в теле — смена только через отзыв и новый сбор. Зона, равная своей, и вторая
  установка с уже занятой зоной — отказ.

Хранится ровно две вещи: строки `metrics_daily` с `zone` зоны источника и
`provenance = 'peer'` (DDL — там же, в `METRICS_SCHEMA`) и одна строка состояния на источник:

```sql
create table if not exists pulse_peers (
  origin text primary key,             -- https://app.remuka.ru: схема и хост, без пути
  zone text not null check (zone in ('eu', 'ru')),   -- зона источника, запоминается при сборе
  last_success_at timestamptz,
  last_day date,                       -- последний день последней успешной выгрузки
  last_rows integer,
  last_error text,
  last_error_at timestamptz,
  received_at timestamptz not null default now(),
  unique (zone)                        -- одна установка на зону: иначе удаление по зоне неточно
);
```

- Тело выгрузки не сохраняется ни на диск, ни в лог; второй копии агрегатов нет.
- Строки `peer` и строка состояния пишутся одной транзакцией: состояние без данных и данные
  без состояния не остаются.
- Строки `peer` перезаписываются `insert … on conflict do update`: источник правды по зоне
  один — отдающая установка.
- Свежесть: если `last_success_at` старше 72 часов, зона показывается как «нет данных с
  <дата>» и не входит в «Все»; итог подписывается «без РФ». Строки при этом не удаляются.
- Копия у получателя — не бэкап: восстановить по ней зону нельзя и не нужно.
- Состояние сбора видно командой `pnpm pulse:peer:list` (чтение, автор не нужен).

### 5.4 Отзыв

Отзыв — с двух сторон, и обе обязательны:

1. **Отдающая сторона** меняет `REMO_PULSE_TOKEN`. Старый токен перестаёт работать со
   следующего запроса: второго токена и льготного периода нет. Это единственный способ закрыть
   доступ, потому что получатель к отдающей базе не ходит.
2. **Получающая сторона** убирает origin из `REMO_PULSE_PEERS` (сборщик больше не ходит) и
   запускает `pnpm pulse:peer:revoke --origin https://app.remuka.ru --reason "…" --as <оператор>`:
   в одной транзакции удаляет `metrics_daily where zone = $1 and provenance = 'peer'` и строку
   `pulse_peers`, пишет аудит `pulse.peer_revoked` с причиной и автором. Панель сразу перестаёт
   показывать зону — без кэша и без «остатков на графике».

Удалить строку из `REMO_PULSE_PEERS` без команды — не отзыв: данные останутся, и панель
продолжит их показывать. Наоборот, команда без правки env бесполезна: следующий сбор вернёт
строки. Повторное включение — снова добавить origin в `REMO_PULSE_PEERS`: сборщик догоняет
200 дней, старое не воскресает, потому что удалено.

Проверка: после `pulse:peer:revoke` в фильтре нет зоны, `select count(*) from metrics_daily
where zone = 'ru' and provenance = 'peer'` = 0, в журнале есть строка с причиной.

### 5.5 Почему нельзя отдавать события и идентификаторы

- **Право.** ADR-254 §5.1: персональные данные между установками не ходят. `org_id`,
  `actor_id`, `session_id` — псевдонимные идентификаторы и остаются персональными данными
  (GDPR ст. 4(1), 152-ФЗ ст. 3). Их передача — трансграничная передача со своим основанием,
  уведомлениями и защитой; агрегаты без идентификаторов — нет. Подавление «<5» существует
  ровно для того, чтобы агрегат нельзя было свести к одной организации.
- **Удаление.** Идентификатор в чужой установке — копия, до которой владелец не дотянется:
  удаление аккаунта (ADR-257) оставило бы след. Агрегат к человеку не привязывается, и удаление
  на своей установке остаётся полным.
- **Безопасность.** Поток событий — это профиль поведения и ключ соединения с продуктовой
  базой. Токен, который отдаёт агрегаты, нельзя превратить в интерфейс запросов к чужой базе;
  токен, который отдаёт события, — можно.
- **Одна формула.** События — сырьё отдающей стороны со своей версией каталога; получателю
  пришлось бы толковать их по-своему, и появилось бы второе определение метрики (правило 1).
  Агрегат считается один раз, владельцем, и едет как факт.
- **Продукт.** Главной метрике нужны команды, а не люди. Всё более дробное — наблюдение за
  клиентами, которое ADR-259 запрещает оператору.

*Юристу:* подтвердить, что (а) передача таких агрегатов из РФ в ЕС не является трансграничной
передачей персональных данных, (б) подавления «<5» достаточно, чтобы строка не считалась
персональными данными, (в) хранение копии агрегатов в ЕС до 730 дней допустимо.

## 6. Панель «Пульс»

Раздел «Пульс» общей консоли `/operator` (`spec/operator.md` §5). Доступна только
`instance_operators` (роль выдаётся командой `pnpm operator:grant`, `spec/operator.md` §2);
остальным — 404. Строится на компонентах `@remo/ui` и токенах REMO 2.0, без
сторонних скриптов (CSP не меняется).

**Верх: фильтры.** Зона (Все / ЕС / РФ), период (4, 12, 26 недель), валюта итога (USD / RUB).

**Ряд 1 — шесть плиток.** Каждая: значение, изменение к прошлому периоду, линия за 12 недель.
1. Совместно работающие команды за неделю — главная, крупнее остальных.
2. MRR — снимок на конец последнего полного дня, без живого запроса к биллингу.
3. Платящие команды и прогресс до безубыточности (полоса «N из 43»).
4. Activation 7d.
5. Retention W4.
6. Новые организации.

**Разделы ниже** — свёрнуты по умолчанию, кроме первого:

| Раздел | Что внутри |
|---|---|
| Рост | Воронка: визиты сайта → регистрации → активация → приглашение → совместная работа → оплата; таблица источников с конверсией |
| Вовлечённость | DAU/WAU/MAU и stickiness; совместные сессии; использование функций (полосы); популярные шаблоны |
| Хром | Элемент — доля активных организаций за 28 дней: `chrome.orgs28` / `active.orgs28`; пороги 5 % и 40 % (ADR-266 §9, ADR-294) |
| Удержание | Тепловая карта когорт по неделям (W0–W12) |
| Деньги | MRR по тарифам и валютам (столбцы с накоплением); Free→paid, Trial→paid; churn, GRR, NRR; упор в лимиты по тарифам |
| ИИ | Задачи, доля применённых, стоимость на применённую задачу, по навыкам |
| Здоровье | Ошибки сохранения, сокеты, недоставленные письма, шлюз ИИ, поддержка |

- У каждой цифры — подсказка с определением и ссылкой на этот документ: никто не гадает, что
  значит метрика.
- Значения, которые нельзя считать (нет данных за период, малые числа), показываются как «—»
  с причиной, а не как 0.
- Кнопка «Выгрузить CSV» у каждой таблицы.
- Графики рисуются по правилам визуализации дизайн-системы: одна ось, подписи прямо на линиях,
  без лишних легенд.

## 7. Еженедельная сводка и пороги

- **Сводка по понедельникам** на адреса из `REMO_PULSE_DIGEST_TO`. Шаблон письма
  `pulse_weekly` (RU), через почтовый модуль (ADR-246): шесть плиток ряда 1 с изменениями к
  прошлой неделе и три самых больших изменения в разделах. Без вложений и внешних картинок.
- **Пороги** — настройка оператора на панели, по метрике и зоне: «Activation 7d ниже 25%»,
  «доля ошибок сохранения выше 0,5%», «неоплаченных продлений больше 3». Превышение — строка в
  сводке и отдельное письмо не чаще раза в сутки.

## 8. Этапы

1. События §2 в каталоге и в коде; `orgs.source`; передача меток при регистрации.
2. **Пульс §4–5: агрегаты и обмен зонами.** `metrics_daily` и её DDL (§4.1); функции
   `compute<Metric>` с тестами на фикстурах; ночной агрегатор, догон и `pulse:recompute`
   (§4.2–4.4); `pulse/peer-collect.mjs`, `pulse_peers`, экспорт с подписью и `pulse:peer:revoke`
   (§5). Готово, когда:
   - миграция применяется на пустой и на существующей базе метрик, а второй прогон
     `pnpm db:metrics` ничего не меняет;
   - агрегатор пишет вчерашний день и не пишет сегодняшний;
   - два прогона `pulse:recompute` за один день (и ночь поверх них) дают одинаковый снимок
     `metrics_daily`;
   - зона A отдаёт, зона B собирает: в `metrics_daily` есть строки `provenance = 'peer'`, и
     ответ `/operator/pulse` содержит обе зоны;
   - в теле выгрузки нет e-mail и пользовательских id;
   - `pulse:peer:revoke` удаляет строки зоны, пишет аудит и убирает зону из панели.
3. Панель `/operator/pulse` на `metrics_daily`: фильтры, плитки, разделы «Рост» и «Деньги».
4. Остальные разделы, CSV, подсказки с определениями.
5. `site-stats.mjs` и `site_daily`; дневной счётчик визитов в `metrics_daily` (`site.visits`).
6. Сводка и пороги.
7. Обновление `spec/metrics.md`: убрать «биллинга нет», сослаться на этот документ.

## 9. Приёмка

- [ ] `pnpm verify` зелёный; у каждой функции расчёта — тест на фикстуре с заранее
      посчитанным ответом.
- [ ] На стенде с `pnpm demo:seed`: WACT, MRR, Activation 7d и Retention W4 совпадают с ручным
      подсчётом SQL-запросами из приложения к этому документу.
- [ ] Регистрация по ссылке с `utm_source=habr` даёт организацию с `source = habr` и строку в
      таблице источников на следующий день.
- [ ] В `metrics_daily`, `site_daily` и ответе `pulse/export` нет ни одного id организации или
      человека, e-mail, IP или User-Agent (тест по схеме и по содержимому).
- [ ] `/operator/pulse` для не-оператора — 404; для оператора открывается меньше чем за 1 с на
      данных за 26 недель.
- [ ] Фильтр «РФ» на установке ЕС показывает агрегаты, забранные с `app.remuka.ru`; при
      недоступной установке РФ — время последнего успешного сбора, а не нули.
- [ ] Разрез «источник» со значением 3 приходит из РФ как «<5».
- [ ] «Пульс» показывает обе зоны: на установке, которая собирает (§5.3), в фильтре есть «ЕС»,
      «РФ» и «Все»; на установке, которая только отдаёт, — своя зона и причина, почему второй
      нет. Итог «Все» складывает только свежие зоны и подписывается, если одна отсутствует.
- [ ] Две ночи подряд не удваивают агрегаты: после второго прогона `pnpm pulse:recompute` за
      тот же день число строк и `sum(value)` в `metrics_daily` те же, что после первого (тест
      сравнивает снимок таблицы до и после).
- [ ] В обмене нет e-mail и user id: адреса из `users` и id из `users`/`orgs` продуктовой базы
      не встречаются ни в теле `pulse/export`, ни в `metrics_daily`; `dims` проходит закрытый
      список ключей из §4.1.
- [ ] Сводка приходит в понедельник; порог, выставленный ниже текущего значения, даёт письмо
      один раз за сутки.
