## Что это

Платёжный сервис подключается один раз на установку, а не в каждой организации: магазин ЮKassa принадлежит установке, и организации не приносят свои кассы. Ключи магазина хранятся запечатанными ключом установки `REMO_KEK`; в выводе команд виден только короткий отпечаток, по которому секрет не восстановить.

Тестовый и боевой магазины — два разных подключения с разными ключами. Перевести тестовое в боевое нельзя: для настоящих платежей создают второе подключение. Тестовое обслуживает только организации с включённым тестовым режимом оплаты и никогда не появляется в публичном каталоге тарифов.

Результат страницы: подключение со статусом `active`, адрес уведомлений в кабинете ЮKassa, полный прайс-лист валюты и проверка, что оплата доходит до установки.

## Где запускать команды

Команды этой страницы выполняются на сервере из каталога установки, а не в дереве разработки: `pnpm` на хосте не нужен. `remo cli` берёт скрипт из образа текущего релиза, читает окружение из `shared/production.env` и монтирует `shared/` в контейнер только для чтения как `/shared`:

```sh
cd /srv/remo
./remo cli billing-providers list
```

На стенде каталог другой: `/srv/stage-ru` или `/srv/stage-eu`.

## Что нужно заранее

| Что | Зачем |
|---|---|
| Тестовый магазин ЮKassa: `shopId` и секретный ключ | ключи подключения; для боевого подключения нужны боевые ключи |
| `REMO_KEK` — 32 байта в base64 | им запечатываются ключи; `list` работает и без него, а `create` с секретом, `verify` и `secret` — нет |
| `REMO_BILLING=on` | при `off`, а это умолчание для self-host, каталог и оплата отвечают 404 |
| `REMO_BILLING_CURRENCIES` с валютой, например `RUB` | каталог предлагает только валюты из этого списка |
| `REMO_YOOKASSA_WEBHOOK_IPS` — адреса или диапазоны CIDR отправителя из опубликованного списка ЮKassa | пустой список отклоняет все уведомления |
| `REMO_TRUST_PROXY=1`, если сервис стоит за nginx | иначе отправителем считается прокси, и уведомления отклоняются |
| `REMO_APP_ORIGIN` — HTTPS-адрес установки | из него строится адрес уведомлений; по нему же снаружи открыт `/api/` |
| Полный прайс-лист валюты: месяц и год для Pro, Team, Business в продаже | валюта без полного прайса не показывается покупателю |
| Роль оператора установки | создание подключения и цены принимают автора `--as` |

## Создать файл секрета

Создайте файл в каталоге `shared/` установки: контейнер видит его как `/shared/...`, а на хосте он лежит вне репозитория и образа. Файл нужен команде один раз и удаляется после подключения или ротации. Внутри — один объект JSON с двумя полями из кабинета ЮKassa.

```sh
cd /srv/remo
umask 077
cat > shared/yookassa-test.json <<'JSON'
{ "shopId": "123456", "secretKey": "test_..." }
JSON
chmod 600 shared/yookassa-test.json
```

`shopId` — номер магазина, `secretKey` — секретный ключ из раздела интеграции. Команда не принимает ключ отдельным флагом: только файл или скрытый ответ в терминале, поэтому секрет не попадает в историю оболочки и в список процессов.

## Создать подключение

```sh
./remo cli billing-providers create --provider yookassa --mode test --currency RUB \
  --groups ru_card --name "ЮKassa тест" \
  --secret-file /shared/yookassa-test.json --as ops@example.com
```

Обратите внимание на путь: на хосте файл называется `shared/yookassa-test.json`, а команде передаётся `/shared/yookassa-test.json` — путь внутри контейнера.

Команда печатает `[billing:providers] created <id> (draft)`, а затем строку с id, `yookassa/test`, статусом, приоритетом, валютой, группой методов и отпечатком секрета. Сам секрет не печатается. Сразу после проверки конфигурации команда обращается к магазину: при успехе печатается `yookassa: the shop is reachable`, при ошибке — причина, подключение остаётся `draft`, а код выхода равен 1. Так неверные ключи видны до первого платежа, а не после него.

`--groups ru_card` — карты российских банков, СБП и кошельки, включённые в магазине. `--name` видит только оператор. `--priority` необязателен: меньшее число выигрывает, когда валюту и группу обслуживают два подключения.

## Проверить подключение

```sh
./remo cli billing-providers verify <id>
```

Команда открывает запечатанный секрет, проверяет магазин и записывает результат в поле «последняя проверка»; статус подключения она не меняет. Успех печатает `[billing:providers] <id> ok: yookassa: the shop is reachable`, ошибка — причину и код выхода 1. Повторяйте после каждой смены ключей, сети или настроек магазина.

## Включить подключение

```sh
./remo cli billing-providers activate <id> --reason "тестовый магазин готов" --as ops@example.com
```

Команда печатает `[billing:providers] <id> is active`. Пока подключение в `draft`, уведомления получают `404`, поэтому включите его до первого платежа.

Позже `pause` останавливает новые покупки, а продления и возвраты продолжаются; `resume` возвращает подключение в работу.

## Взять адрес уведомлений

```sh
./remo cli billing-providers webhook-url <id>
```

Команда печатает `https://<адрес установки>/api/billing/webhooks/<id>/<token>`. Префикс `/api/` обязателен: без него запрос попадает в страницу приложения, которая отвечает 200 и ничего не делает.

1. В кабинете ЮKassa откройте HTTP-уведомления и вставьте адрес.
2. Отметьте только `payment.succeeded` и `payment.canceled`.
3. Не включайте уведомления о возвратах: установка принимает только события платежа, на остальные отвечает `401`, и сервис будет повторять доставку.

ЮKassa не подписывает уведомления. Установка верит двум фактам: адрес отправителя входит в список `REMO_YOOKASSA_WEBHOOK_IPS` и повторный запрос платежа через API с ключами магазина подтверждает статус. Статус из тела уведомления не используется, поэтому подделка тела без ключей ничего не меняет. Уведомление со статусом «ожидает» подтверждается, но платёж не двигает.

## Опубликовать прайс-лист

```sh
./remo cli billing-prices seed --currency RUB --pro 29000 --team 59000 --business 119000 \
  --as ops@example.com
```

Команда создаёт черновики на месяц и год для каждого платного тарифа. Год по умолчанию равен двенадцати месячным суммам; своя годовая цена задаётся флагом `--year-<тариф>`. Суммы — целые минорные единицы: `29000` — это 290,00 ₽.

Каждый черновик публикуют отдельно, по id из вывода:

```sh
./remo cli billing-prices publish pro-rub-month-v1 --as ops@example.com
```

Затем проверьте полноту:

```sh
./remo cli billing-prices check
```

Команда печатает `RUB: complete` или `RUB: incomplete, missing …` и выходит с кодом 1 при пропуске. Валюта без полного прайса не показывается покупателю.

Одну цену добавляют командой `billing-prices add`: она создаёт новую версию в черновике, например `./remo cli billing-prices add --plan pro --interval month --currency RUB --amount 34900 --as ops@example.com`. Опубликованная сумма не редактируется: новая цена — это новая версия, а действующие подписки остаются на своей.

## Проверка

- `./remo cli billing-providers list` показывает строку `active`, `yookassa/test`, валюту `RUB`, группу `ru_card` и отпечаток секрета; самого ключа нет ни в выводе, ни в журнале. Команда работает и без `REMO_KEK`: ключ нужен только для расшифровки.
- `curl -s -o /dev/null -w "%{http_code}\n" -X POST https://<адрес установки>/api/billing/webhooks/<id>/wrong` возвращает `404`: адрес проходит через прокси до сервиса. Любой неверный токен даёт тот же ответ, поэтому проверка подтверждает маршрут, а не токен.
- `curl -s https://<адрес установки>/api/billing/catalog` показывает валюту с ценами и способами оплаты, если есть боевое подключение в статусе `active` и полный прайс. Тестовое подключение в этом ответе не появляется никогда.
- Тестовый платёж на минимальную сумму: плательщик попадает на страницу ЮKassa, платит и возвращается, а в консоли на вкладке **Деньги** → **Подключения** в колонке **Последнее событие** появляется время. Платёж виден в карточке клиента.
- Владелец организации на вкладке «Тариф и оплата» видит тариф, статус, сумму, дату продления, кредит, счета и сохранённый способ оплаты: платёжную систему, последние четыре цифры и срок. Пока продавать нечего, панель говорит, что оператор ещё не опубликовал полный список цен и способ оплаты.

Оплата считается принятой, когда счёт в карточке клиента стал оплаченным. После подтверждённого `payment.succeeded` сервис сам, обычно за пару секунд, применяет платёж только вперёд, закрывает счёт, открывает период подписки, пишет строку `billing_events` и ставит письмо `payment_succeeded` в очередь. Повторная доставка того же уведомления и отмена, пришедшая после успеха, ничего не меняют.

Если уведомление не пришло, раз в час сервис сам переспрашивает у провайдера платежи в состоянии «ожидает» старше 15 минут и применяет ответ тем же кодом. Поэтому платёж, о котором молчит вебхук, обычно закрывается в течение часа.

## Если событие в «мёртвых»

Событие, которое не удалось применить восемь раз подряд, получает `dead_at` и появляется в консоли на вкладке **Деньги** → **Мёртвые события** с кодом последней ошибки. Само оно больше не повторяется.

1. Прочитайте код. `PAYMENT_NOT_FOUND` — событие ссылается на платёж, которого нет в базе (чужое подключение или удалённая строка); `AMOUNT_MISMATCH` / `CURRENCY_MISMATCH` — сумма или валюта у провайдера не совпали со счётом; `INVOICE_NOT_FOUND` — счёт исчез.
2. Сверьте платёж в кабинете провайдера. Если деньги действительно пришли, подтвердите счёт вручную командой `billing-mark-paid` (нужны причина, код второго фактора и `--as`). Такой платёж будет помечен ручным и не будет связан с возвратом через ЮKassa.
3. Если деньги не пришли, ничего не подтверждайте: счёт остаётся открытым, а плательщик может оплатить его снова. Причину ошибки лучше разобрать до следующего платежа — например, проверить адрес уведомлений и список `REMO_YOOKASSA_WEBHOOK_IPS`.

## Стенд

- При `REMO_STAGE=1` команда `create --mode live` отказывает до обращения к базе: `live payment connections are refused on a test stand: create a --mode test connection`.
- Провайдер `fake` доступен только вне production и только с `REMO_PAY_FAKE=1`; иначе команда отвечает `the fake provider is for development only`. Процесс в production с этим флагом не стартует.
- Для тестового платежа нужны тестовый магазин и подключение `--mode test`: тестовое подключение не попадает в публичный каталог, поэтому платные тарифы в панели остаются недоступны с объяснением причины. Это ожидаемо, а не дефект.
- На стенде не используйте настоящие деньги и боевые ключи.

## Если что-то пошло не так

| Симптом | Причина | Что делать |
|---|---|---|
| `[billing:providers] health check failed: YOOKASSA_401` | магазин отклонил ключи, или ключи от другого магазина | проверьте `shopId` и `secretKey` в кабинете, повторите `secret`, затем `verify` |
| `[billing:providers] health check failed: YOOKASSA_NETWORK` | установка не достучалась до `api.yookassa.ru` | проверьте исходящий HTTPS и повторите `verify`; статус подключения не меняется |
| `REMO_KEK is required (32 bytes, base64)` | ключ установки не задан или не той длины | задайте `REMO_KEK` в окружении сервиса; `list` работает без него, но открыть или запечатать секрет нельзя |
| `--secret-file must contain one JSON object` | в файле не один объект JSON | оставьте в файле только `shopId` и `secretKey` |
| `--secret-file: cannot read …` | файл не найден или недоступен внутри контейнера | проверьте, что он лежит в `shared/` установки, а в команде указан путь `/shared/...`, и права 600 |
| `secret needs a terminal` | команда запущена без терминала и без файла | передайте `--secret-file /shared/...`: пайп не может ввести секрет |
| уведомление получает `404` | неверный id или токен, либо подключение в `draft` | возьмите адрес заново командой `webhook-url` и включите подключение |
| уведомление получает `401`, в логе сервиса `not verified` | список адресов пуст, адрес отправителя не входит ни в один адрес или диапазон, или за прокси не задан `REMO_TRUST_PROXY=1` | перечислите адреса и диапазоны из опубликованного списка ЮKassa (например `185.71.76.0/27`) и включите доверие прокси |
| `webhook-url` печатает `localhost` | не задан `REMO_APP_ORIGIN` | задайте HTTPS-адрес установки и возьмите адрес заново |
| каталог пуст, панель говорит о неполном прайсе | нет полного прайса, нет боевого активного подключения или валюты нет в `REMO_BILLING_CURRENCIES` | `./remo cli billing-prices check` и `./remo cli billing-providers list`; для продажи нужно боевое подключение |
| после оплаты счёт остался «ожидает оплаты» | уведомление не дошло, пришло с ошибкой или попало в «мёртвые» | проверьте «Последнее событие» и таблицу «Мёртвые события» на вкладке **Деньги**; платёж старше 15 минут сервис переспросит сам в течение часа. Если деньги пришли, а событие в `dead`, подтвердите счёт командой `./remo cli billing-mark-paid` — такой платёж не связан с подключением, и вернуть его через ЮKassa нельзя |
| `a connection cannot go from … to …` | команда не подходит к текущему статусу | посмотрите статус в `list` и выберите разрешённый шаг |
| `refusing to disable … live subscription(s)` | через подключение ещё продлеваются подписки | сначала `retire`, дождитесь перехода плательщиков на другое подключение, затем `disable` |

## Безопасность и выключение

- Секрет передаётся только файлом или скрытым ответом в терминале. Флаг для ключа команда не принимает, поэтому секрет не остаётся в истории оболочки, в списке процессов и в выводе.
- Файл живёт в `shared/` установки, вне репозитория и образа, с правами 600; удалите его сразу после создания подключения или ротации.
- Наружу виден только отпечаток. В журнале и в консоли секрета нет.
- Потеря `REMO_KEK` делает сохранённые ключи нечитаемыми: храните его вне сервера и в резерве.
- Ключи существующего подключения меняют командой `secret`: новый секрет запечатывается, пишется аудит с отпечатком, затем магазин проверяется. Если проверка не прошла, подключение уже несёт новый секрет, поэтому держите старый файл до успешного `verify`. Сохранённую карту перенести между подключениями нельзя: плательщик один раз вводит её заново.

```sh
./remo cli billing-providers secret <id> --secret-file /shared/yookassa-new.json \
  --reason "плановая ротация" --as ops@example.com
```

На `manual` команда отказывает: у ручной оплаты секрета нет.

| Команда | Что останавливается | Что продолжается |
|---|---|---|
| `pause` | новые покупки | продления по сохранённым картам, возвраты, уведомления |
| `resume` | — | всё, как до паузы |
| `retire` | новые покупки через это подключение | продления по сохранённым картам, возвраты |
| `disable` | новые покупки и продления | возвраты и уведомления; запись остаётся навсегда |

`disable` отказывает, пока через подключение продлевается хотя бы одна подписка, и перечисляет их. Удалить подключение нельзя: с историей платежей оно остаётся в статусе `disabled`.
